# Native L5 maintenance

With `EIMEMORY_L5_LOOP_ENABLED=1` and `EIMEMORY_L5_LOOP_APPLY=1`, nightly uses the same bounded system detector, incident router and transaction recovery owner as `learn watch --apply`. A watch without `--apply` does not write incidents or resume effects. Existing transaction recovery remains available when a new detector or proposal fails.

After quality, capability evolution and code maintenance, nightly persists one native v4 reader envelope, verifies its archive and retains the current deployment receipt and release session. Capability selection may use the configured product scope only through the existing operator alias grant. Business quality and code transaction ownership stay on the exact report scope. A reliable capability snapshot is not a terminal repair receipt.

The runtime identity detector uses owner-bound `runtime_identity_drift.v2` identities. Time belongs to the observation, so concurrent observations of the same fault retain one immutable first incident. A separate current observation prevents a recovered or replaced fault from being proposed again. Historical v1 incidents remain historical. Missing or corrupt current authority blocks routing rather than implying recovery.

Source-specific quality and incident reads, and exact-owner repository ledger reads, apply their SQL filters before their result bound. A full sentinel page or corrupt physical/payload identity is an incomplete read. It cannot silently certify absence or fall back to another owner's evidence.

## Policy operator commands

Use the actual current native incident's SHA-256 digest and registered class, detector and protected test plan. `deploy/code-automation-policy.v2.json.example` describes a structure; its placeholder digests and historical timestamps are not deployable authority.

```sh
eimemory learn code-evolution-policy-issue \
  --incident-class deployment.runtime_commit_drift \
  --detector-id eimemory.runtime_identity_drift.v1 \
  --incident-digest "$CURRENT_NATIVE_INCIDENT_SHA256" \
  --test-plan-id deployment.runtime-identity-drift.v1 \
  --max-transactions 1 \
  --effects all-disabled

eimemory learn code-evolution-policy-validate \
  --path /etc/eimemory/code-automation-policy.v2.json \
  --incident-digest "$CURRENT_NATIVE_INCIDENT_SHA256" --json
```

Issuing without `--install-path` prints a policy. Installation uses a complete private temporary file and atomic replacement, rejects symlink paths, and requires a clean repository. The installed policy must be private and owned by the runtime user: a root-owned mode-600 file is not readable authority for a `darrow` runtime. Enable the intended effects explicitly through the existing protected operator policy. Validation uses the same native policy loader as the router and opens no runtime database. It validates policy authority; the router still checks the actual current incident, exact owner, repository, provider and one-shot limit.

`execution_ok`, `control_plane_ok` and `product_l5_complete` are separate results. A valid archived assessment awaiting an autonomous terminal receipt or its required observation window is reported in `l5_evidence_waits`. Execution errors, invalid existing proofs and negative evidence remain failures. Qualified historical business samples continue to count as business evidence; they do not invent an autonomous code transaction or shorten the native eight-hour observation requirement.

The installer verifies a persisted current-release receipt before dispatching maintenance. Installing or enabling timer metadata alone cannot start a first-install watcher. A receipt or native read-back failure blocks restoration and retains the deployment rollback boundary.

## Native incident delegation

The maintenance owner can derive one child policy from a standing grant only after the shared native selector verifies an exact current incident, owner and release. Each exact scope has one path `/etc/eimemory-code-automation-authority/scope-<digest>.v1.json`; `standing_grant_path(scope)` computes the canonical SHA-256 of its four coordinates. The owner reads only its own path, without scanning or falling back to another scope. Its parent must be root controlled, with no group/other write permission, and the regular, single-link grant must be root owned mode 600 or 640. A typical root:darrow directory uses 750 and its grant uses 640. The runtime reads this authority; it never creates a standing grant. `/etc/eimemory` is writable by the runtime and cannot serve as the standing authority directory.

The `code_automation_standing_grant.v1` contract names the grant ID, enabled flag, timezone-aware `not_before`, required `expires_at`, exact four-coordinate scope, repository root/remote/branch/remote-URL digest, Profile key and digest, registered class/source/detector/test-plan/digest routes, the five exact effects and a transaction limit of one. Explicit JSON null for `expires_at` means standing authority until root revocation; otherwise it must be a future timezone-aware timestamp. Missing, empty, boolean or numeric expiry is invalid. Missing, expired, disabled, revoked, unsafe or mismatched grants deny new delegation. Global `standing-grant.revoked`, per-scope `scope-<digest>.revoked`, or the existing code-evolution kill switch denies delegation. Healthy owners without a current incident stay idle without depending on a grant. Each child still expires within two days and permits only one transaction; standing validity never extends its observation or consumption contract.

The executable preparation entry is `python -m eimemory.governance.evolution.code_automation_policy_grant prepare`. Run it as the actual runtime service user, with `--runtime-root`, the four `--scope-tenant/agent/workspace/user` values from the current native report and `--profile-key` from its actual configured Profile. Omitting `--valid-hours` prepares explicit null expiry; a positive integer requests a finite interval. It resolves existing release/Git/Profile coordinates, requires an actual `code.implementation` requirement and generates a real UUID, current interval and protected-plan digests; it requires no incident and creates neither authority nor a sample. An empty Profile cannot create useful repair authority. Preserve its JSON output for review. Preparation as root is rejected so it cannot initialize a production SQLite store under root.

After review, the root-only `install` subcommand accepts `--prepared`, the exact reviewed `--expected-grant-digest`, and the independent POSIX `--runtime-user`. Logical scope users may be channel `ou_*` identities; they need not equal the service account `darrow`. The repository and its Git entry must belong to that service account. All installation Git reads run as that account through fixed read-only arguments and a clean environment; root neither ignores dubious ownership nor executes runtime Git configuration. Installation creates the protected directory and root-owned grant, validates its read-back, and constructs no Runtime or child policy. Existing different standing authority is preserved unless the operator supplies its exact `--replace-digest`. An absent trusted repository configuration, clean current release, exact Profile or matching protected-plan contract is an explicit prerequisite failure; no placeholder value is substituted.

New preparation also records a `capability_authority` snapshot naming the exact incident owner, configured provider scope, code.implementation operation, Profile digest and authorization basis. The optional root-controlled code-provider delegation authorizes only these provider/Profile/catalog/advertisement reads; it changes neither global identity aliases nor memory, incident, business receipt or release authority. The standing grant, original intent and delegation receipt retain that whole snapshot, and maintenance carries it to the router and proposal. Current authorization and Profile are rechecked before publication and effects. Older grants and transactions without a snapshot retain their original exact-owner lookup; a later root mapping cannot silently lend them a new provider.

The provider mapping lives at `/etc/eimemory-code-automation-authority/code-provider-delegations.v1.json`, using schema `code_provider_scope_delegations.v1`, enabled true and at most 32 unique-owner entries. Each entry names exact owner/provider four-coordinate scopes, the same tenant/agent, code.implementation, global scope, propose_patch_v2, and the actual Profile key/digest. Wildcards and an unconfigured target are rejected. Root controls the single-link regular file at 600 or 640 and its parent at 750 without group/other write permission. Mapping and standing-grant installers serialize on `.standing-grant.install.lock`. Revoking this mapping prevents new delegated provider use while existing safe rollback remains available.

Only native runtime-drift and current captured closure routes support automatic delegation. Router-policy-failure incidents retain the existing manual policy path until they have an independent currentness fence. The model chooses no path, class, effect, command or test plan. Authority code, the shared selector, provenance contract and capture producer are in DENY_SELF.

The child remains a private runtime-owned v2 policy. An existing manual policy is preserved. Native publishers share a bounded lock and compare the exact prior policy digest before atomic publication, then fsync the parent directory and verify the exact original bytes with the strict native loader. The owner persists its original intent, policy bytes and real issuance/expiry timestamps before publication. A restart reuses that intent; renewing a grant cannot reset the incident/release one-shot identity or its SQLite consumption. Grant or publication failure still leaves existing transaction reconciliation and rollback available.

The common repository retains one serialized child policy across owners. An unused prior policy can be replaced only after its own exact owner has verifiable native current-source evidence that supersedes the original incident. A different owner's incident cannot retire it; missing or corrupt currentness blocks handoff. A consumed prior transaction must belong to that original owner and have its real matching terminal receipt. First publication and crash replay both repeat these checks before replacing authority, retaining original bytes, times and consumption.

Every non-inspection native closure capture declares its current scope/commit marker at the start and completes only its own still-current marker. A newer successful, partial, failed or in-flight capture prevents fallback to an older failure. Reading this fence revalidates original source bytes, structural verdict, decision digest and exact receipt/session; the marker supplies no CPA/HMAC, latest complete inventory, novelty, terminal or elapsed-observation evidence. Legacy captures without the marker remain auditable through the manual path.

## Original incident facts

A native detector observes a failure; that observation does not establish the absence of prior human knowledge or reports. Runtime-drift, closure and router-failure producers retain those unsupported facts as JSON null. Explicit original adverse facts stay true. A self-consistent SHA-256 snapshot does not prove a negative. Old native signed declarations remain intact, but their formerly unconditional false values normalize to unproven for L5 qualification, with declared values retained for audit.

New ledger rows use `code_evolution_transaction.v2` and a canonical, digest-bound `code_incident_provenance.v1` snapshot in both payload and source evidence. The existing SQLite boolean columns cannot represent null; for unknown they contain the conservative nonqualifying guard `1`. These physical guards are not public provenance facts. Every native ledger read validates the encoding, schema, digest, payload, nested proposal and physical projection before returning the original bool/null values. Missing or contradictory typed evidence fails closed, including terminal receipt read-back. Metadata updates cannot rewrite the original source facts. Existing legacy boolean rows and immutable receipts are not rewritten. Idempotent legacy create/replay compares the original encoding, source and explicit facts, then returns the original row; altered or removed declarations conflict.

Permission to repair is independent of L5 qualification. Unknown facts may accompany a strictly authorized repair and a healthy observation, while remaining explicit unproven gaps. L5 requires explicit proven negatives for all three source facts, including non-manual origin, plus its independent terminal, source, provider, lineage and full 28,800-second observation gates. Known adverse facts and corrupt evidence remain failures; missing facts never become false during proposal serialization, SQLite projection, terminal capture, archive or nightly diagnostics.

Readiness keeps the existing 200 ms RPC probe and 250 ms fragment deadlines. Active-memory authority heads use a covering keyset index; a busy reader pool waits for a returning reader within that same deadline. An already submitted backend worker retains single flight until it ends, including a deadline expiring before the Future wait begins. These repairs add no business samples, reset no failed evidence, and certify no L5 terminal receipt or observation period.

In 1.14.152, controlled qualification waits for a real read-only current-projection proof before sampling. Release replay and live gates can write memory, so the release workflow rechecks the vector projection and the authenticated listener after replay and after the full observation window. Both must identify the same authority revision and watermark. This bounded settling phase does not enlarge the original recall or readiness-probe budgets, retry an actual failed stability sample, or certify L5 completion.
