# Managed code knowledge provenance

This is the explicit `registered_code_defect_knowledge.v1` domain. It does not
assert the absence of knowledge in people's minds, external messages, ordinary
free text, PostgreSQL, or sources outside the root-reviewed registered typed
code ingress. The original three global provenance facts remain `None` or true.
Legacy v4 qualification continues to require its original explicit negatives.

The reviewed manifest registers the four native typed ingress sources (three
detectors and code-maintenance reports), exact owner scopes, physical SQLite
capture schema, current producer bytes, and the retained typed-history boundary.
Unknown typed incidents, unavailable source payloads, mutated ingress, capture
gaps, late prior reports and unfinished history scans cannot prove absence.
The persistent root-owned knowledge registry does not reset at a coverage epoch,
release, producer update or policy replacement. A typed defect key contains the
registered affected contract and original static diagnostic codes; it excludes
release IDs, receipts, grants and time. Unknown/dynamic codes cannot be keys.
The explicit key semantics are `conservative_native_symptom_signature.v1`.
This is a symptom signature, not a causal failing-code identity. A genuinely
different defect producing the same typed symptom remains conservatively known;
the original reports do not establish that its cause differs. The mechanism
does not claim to remove this remaining source-information limit. A future
failing-code/fault-state identity requires actual typed producer evidence, with
its own reviewed codec; a new release/hash/epoch cannot substitute for it.

Before an original detector source is appended, it records the root manager's
actual activation receipt reference. Source creation/receive time is native and
precise. An idempotent replay preserves the original bytes and activation. The
issuer verifies that original receipt, including actual job/InvocationID cause;
an old manual or unknown source cannot borrow a later timer invocation. Signed
unknown activation remains unknown. `TriggeredBy` and a stale unit activation
property are not scheduled-origin evidence.

Authority paths are fixed within the host manager's existing protected trees:

* `/etc/eimemory-code-automation-authority/managed-code-incident-manifest.v1.json`
  is root-owned 0640 and its raw SHA is pinned in the root manager registry.
* `/etc/eimemory-code-automation-authority/managed-incident-proof.key` is root-only
  0600. It is never readable by the runtime account or returned over the socket.
* `/var/lib/eimemory-manager/managed-incident-receipts` is a root-controlled
  directory containing immutable HMAC receipts and `knowledge.sqlite`.
  `empty-pycache` is root-controlled, empty and not writable by the runtime UID.

The installed stdlib-only authority module never imports writable product code
as root or opens the runtime SQLite database. It launches a fixed UID 1001 worker
with URI `mode=ro`, `query_only`, a SELECT-only authorizer, and raw producer byte
guards before and after. Root requests accept only original source ID and digest;
scope, paths, facts and negative assertions are not caller parameters.
The fixed worker uses `/usr/bin/python3 -I -S -B -X pycache_prefix=<protected-empty-directory>`.
The complete Python source inventory excludes only the unsearched root `.venv`,
root `.git` and `__pycache__` directories. It still detects any added source
package Python file and permits legitimate empty `__init__.py`. Every source
file and ancestor's inode/device/ctime/mtime/mode identity must remain unchanged
across worker execution, including a change followed by restoration of bytes.

Issuance incrementally accumulates at most 5000 actual global receive rows per
call. An unfinished prefix is explicitly unproven. Every positive typed key is
kept across releases. A receipt is signed only after an independently bound
source, complete prefix and registered retained typed history have been checked.
Original root receipt bytes/timestamps are reused on replay. Verification is
strictly read-only, including root state; subsequent rows are evaluated in a
bounded memory snapshot. A late or adverse observation rejects an old proof
rather than rewriting or re-signing it. The verification endpoint returns the
original immutable snapshot and a separate current-knowledge result. This lets
an authorized repair retain its real source while v5 qualification becomes
unknown/adverse. Invalid signatures or changed original sources still fail
closed. Root configuration starts disabled.

Healthy watch/nightly maintenance explicitly calls the no-argument managed
knowledge checkpoint endpoint. It accumulates original receive rows and positive
history even when no incident exists, and never creates a negative proof, incident
or child policy. Issuance and checkpoint lock acquisition have a native monotonic
10-second bound; each physical worker is limited to 60 seconds and each source
guard to 10 seconds. The host-manager client uses a 120-second managed-operation
budget. A timeout is an unknown outcome: retry only the exact original source
identity and re-read its immutable indexed receipt.

Prepare a real manifest using the installed release's unprivileged account and
`python -B -m eimemory.ops.prepare_managed_incident_authority`, with required
`--source-directory`, exact `--commit` and one `--scope` JSON per actual owner.
The command reads the fixed runtime SQLite database and prints a candidate to
stdout. It performs no installation and includes actual source hashes and capture
schema. The host-root manager's separate explicit enable operation must review
and pin those raw bytes, create the private key/directories and call the stdlib
`validate_configuration(registry=...)` preflight. The default stays disabled until
those actual prerequisites are satisfied. Manifest updates carry the previous
canonical manifest digest; they do not reset positive knowledge or watermarks.

Managed completion uses explicit `l5.reader.v5` / `l5_readiness.v5` envelopes and
the domain above. The immutable snapshot appears in proposal, both transaction
mirrors, typed v4 ledger source evidence and the terminal receipt. Every current
qualifier re-reads the root original and current knowledge. v4 reports retain
the original global semantics; bounded diagnostic receipts cannot upgrade them.

The domain proof supplies no permission to repair. Root standing grants,
one-shot machine authorization, protected tests, provider identity, actual effect
receipts, current lineage and the real minimum 28800-second observation window
remain independent requirements. No production incident, child policy, terminal
receipt or observation is created by installing the provenance mechanism.
