# memory.recall 自然问法召回改进方案

日期：2026-09-07。检查基线：`1.11.83 / 183983099fd0b8d051e45c53968b1600acae7133`。

结论：先修候选召回和评测失真，再用同一数据集验证排序，最后建立当前发布的正式报告与 strict 状态。仅补齐报告或调整融合权重，不能解决目前暴露的自然问法问题。

本次完成 GitHub 快进同步、代码检查、隔离诊断和相关测试；本文是待实施方案。用户提供的生产 22/22、3 条显式查询首位命中、自然样本 10/15，以及两个实际漏召回案例，本次未重新连接生产独立核验。隔离实验使用人工构造记忆，不代表用户真实微信偏好或福建供电事实。

## 第一轮：明确故障在哪一层

### 已确认的代码行为

1. **最新修复范围有限。** `eimemory/retrieval/engine.py:1159` 将融合时向量参与条件从大于 0 改为至少 0.12；这能减少弱向量错误投票，但不会产生新的同义候选。
2. **默认 SQLite 召回依赖词面信号。** `eimemory/embeddings/local.py:27` 是 128 维 token/字符三元组哈希；`eimemory/storage/sqlite_store.py:4032` 的 `semantic_score` 是字符 n-gram Jaccard。二者不提供经过训练的语言语义表示。
3. **候选先筛选，随后才融合。** `sqlite_store.py:4181` 先按全文、锚点、分区种子和最近记录构造有界候选；`sqlite_store.py:4058` 可因词面、字符和哈希分数不足丢掉记录。正确记忆在这里消失，后续重排无法补救。
4. **真正的稠密向量通道已存在，但可降级。** `eimemory/retrieval/postgres_vector.py:1062` 先取得 SQLite 结果，再根据配置、索引水位、模型指纹等决定是否加入 PostgreSQL 向量结果。生产是否启用、是否因错误旁路，必须逐次查询核实，不能根据本地默认源下结论。
5. **不同向量分数目前被混合。** `postgres_vector.py:1910` 对同一候选的两个 `vector_score` 取最大值；本地哈希相似度与稠密模型余弦分数应保留不同来源和校准信息。
6. **空结果在自然采集链中不可见。** `eimemory/evaluation/production_query_dataset.py:37` 用内连接要求 decision 存在 item；采集和验证又要求非空候选。隔离实验创建一条有结果决策、一条空结果决策，只采集到 1 条，且 `skipped` 为空。该实验只验证采集行为，不是合格生产证据。
7. **自然评测重建了问题。** `eimemory/evaluation/real_query_gate.py:1634` 拼接 `terms + entities + intent`，并使用 `precision` profile。它验证的是脱敏特征查询，不完全等价于用户原句和在线参数下的结果。
8. **显式与自然证据的分离是当前契约。** `eimemory/evaluation/explicit_recall.py` 明确返回 `acceptance_only`、`natural_benchmark_eligible: false`。不能把 3 条显式验收搬入自然样本以满足数量要求。

### 隔离复现实验

使用 2 条人工构造记忆和 8 个查询，在默认 SQLite 源、相同精确 scope/source 下调用真实 `MemoryAPI.recall`：

| 查询类型 | 结果 | 说明 |
| --- | --- | --- |
| 2 个标题查询 | 2/2 命中 | 精确身份查找有效 |
| 4 个保留部分原词的改写 | 4/4 命中 | 词面匹配仍能提供候选 |
| 2 个词面差异较大的改写 | 0/2 命中 | 存储候选报告计数为 2，评分后没有候选，融合输入为 0 |

这证明当前默认路径存在同类质量缺口，但不证明生产两次失败具有完全相同原因。也不能据此断言所有同义问法都失败。

### 第一阶段的交付物

为用户的两类生产问题保存受控的诊断包：原句、清洗后的实际查询、预期记录的精确引用、scope/source、记录类型及可见性、引擎/模型/索引版本、各路候选与排名、过滤原因、最终 bundle 与实际渲染内容。复用现有 explanation、capture 和报告机制。

每个失败必须定位为以下一个或多个环节：记录不存在或不可读、索引缺失或过期、权限/类型过滤、候选筛选、融合排序、最终上下文截断。对福建问题先定位有来源的原始记忆；如果事实没有进入耐久记忆，应修采集或提炼链，不能编造答案或靠检索权重解决。

## 第二轮：修召回，再验证排序

### P0：固定问题集和可观察性

- 将真实失败原句及正确记录引用固定为缺陷回归集。人工改写只进入离线鲁棒性集，明确标记来源。
- 每类问题至少覆盖标题、保留原词的改写、低词面重叠、简称、上下文指代，以及“知识库本来没有答案”的问题。
- 加入过时偏好、相似但不同地区的供电事件、无关通知记录及至少数百条干扰记忆，验证候选预算耗尽时的行为。
- 将原始用户查询、清洗查询和可选扩展查询分开追踪。只使用当前会话已提供的上下文消解指代，不能从答案反向生成检索词。

### P1：恢复可靠的语义候选通道

- 逐查询确认现有 PostgreSQL 向量源的真实参与状态：配置、模型及维度、投影版本、权威记录修订号、索引水位、旁路原因、耗时和目标记录是否有有效投影。
- 若语义通道未启用或经常旁路，先修配置/同步可靠性；若它正常参与但目标仍排在候选之外，再评估表示质量及召回参数。
- 保留原查询的全文/身份/锚点通道，同时为语义候选提供独立有界预算。首轮可在固定开发集比较 48、96 等预算，再按质量与延迟决定；不把扩大最终返回数量当作修复。
- 保留 source/scope 过滤及权威记录再读取。新增候选只能来自当前调用已经有权读取的分区。
- 中文词面通道使用有界、稳定的分词或滑动 n-gram，并验证加一个语气词不会让关键词切分错位。当前 lexical 的中文二字块按步长 2 切分，应纳入比较。
- 对已确认的实体别名、地区简称和常见表达做受控扩展；“微信”“福建”只能作为回归样例，不能写成专用业务规则。扩展结果不自动变成身份别名或 ground truth。
- 优先使用仓库已有语义接口。只有真实通道表现不足，且固定评测证明收益时，才考虑更换 embedding 或新增模型依赖。

### P2：校准融合与相关性判断

- 将本地哈希、稠密向量、词面、图关系保留为可辨认的分量。不要把两种分数取最大值后共同套用一个阈值。
- 对各分量分别评估噪声、相关性和冗余；原词、扩展词及哈希高度相关，不能因为来自多个列表就重复获得完整投票优势。
- 候选召回达标后，再比较现有 RRF 与有界重排方案。需要时仅对前 20–40 个已授权候选重排，并限制延迟。
- 审查前后筛选阈值的含义是否一致，包括 `engine.py:1553` 返回多个分量最大值的兜底行为。分数不足时应暴露证据不足状态，而非通过无条件降阈值填满结果。
- 核对微信偏好是否具有正确 memory_type；核对福建事实是否被误分为报告、原始对话或运行诊断。分类问题通过可追溯迁移修正，保留原始来源。
- 验证最终渠道渲染后仍包含支撑答案的信息。内部 Top-5 命中不等于用户实际获得了相关内容。

### 用逐项对照决定是否保留改动

在同一冻结数据、相同来源权限和可比运行条件下分别比较：现状、只修语义通道、加入候选预算/词面改进、再加重排。每一步记录候选命中、最终排名、误召回和延迟；没有稳定收益的改动不进入发布。

## 第三轮：让验收能够发现失败

### P0：修自然采集的空结果盲区

- 以真实查询决策为主记录，返回 item 可以为零；同时更新采集、pending 验证、标注和数据集读取契约，不能只把一处 JOIN 改成 LEFT JOIN。
- 以决策数分页，避免返回条目数量挤占查询样本预算。报告 raw、eligible、pending、labelled、accepted 数量及每类拒绝原因。
- 正确答案标注独立于返回列表，允许标注实际漏掉但调用有权读取的耐久记忆。允许真实的无答案判断，单独统计误召回，不把它计作正例召回成功。
- 复用既有服务器来源、版本绑定、精确引用和标注校验，不为通过验收制造 proactive decision。

### P1：补 Codex 的真实自然观测

- 沿真实会话入口核查 Codex 是否调用既有 `adapter.proactive.prefetch`，以及会话、轮次、来源、发布绑定和消费结果是否到达服务器。
- MCP `eimemory_recall` 当前属于显式路径；即使 `acceptance_generated=false`，也不能自动满足现有自然 proactive 基准。
- 若要评估真实用户显式提问，另设明确的观测分层和资格契约，并保留现有主动召回门禁。不能把显式与主动混合计数。
- 从真实使用中积累合格 Codex 样本并完成独立标注。当前契约每个渠道至少 5 条、总数至少 15 条；这是覆盖门槛，不是质量分数，也不是充分的泛化证明。
- 按会话和语义问题簇划分开发集、留出集，避免同一问题的五种改写同时成为“五个独立自然样本”。

### P2：增加忠实于原问法的质量报告

- 保留现有脱敏特征评测的历史口径，同时增加原句或经过核验的保义脱敏原句测试。报告只记录受控引用/摘要，原文保存在授权的私有数据域。
- 在线观测与离线重新运行分别计分：前者衡量用户实际得到的结果，后者用于同样本比较新旧引擎。不得用稍后的成功结果覆盖原先的失败。
- 测试在线实际参数、各渠道真实入口和最终渲染结果，并另保留统一参数的引擎对照结果，避免 profile 差异掩盖问题。
- 旧记录只有摘要或 digest、无法恢复原问法时，标记为原句不可验证；不能凭标签补写原问题。
- 评测契约、模型、候选策略或词表变化都应版本化。不同口径的数字不直接作为相同基线对比。

### 验收标准与发布顺序

| 层次 | 验收条件 |
| --- | --- |
| 问题定位 | 两类真实失败均有精确引用、完整路径和可复现失败阶段 |
| 缺陷回归 | 用户原始失败查询全部恢复；标题命中保持；没有泄露、错误偏好或无依据供电答案 |
| 候选覆盖 | 建议留出正例集 Candidate Recall@50 ≥ 95%；按渠道与问题类型报告，不使用它替代最终质量指标 |
| 最终质量 | 沿用现有 Recall@5 ≥ 0.90、Precision@5 ≥ 0.20、MRR ≥ 0.80、NDCG@5 ≥ 0.80；同时验证原问法与错误召回 |
| 性能与稳定性 | 沿用现有 p95 ≤ 3000 ms、内存、基线稳定性和来源隔离门禁；不可用通道显式报告降级 |
| 自然覆盖 | 三渠道各至少 5 条合格自然样本，显式验收和人工改写单独展示 |
| 发布证明 | 正式报告绑定实际部署提交、数据集与检索身份；strict 验证通过且引用同一 gate |

15 条仅是最低覆盖门槛。建议继续形成至少 50 条、覆盖不同会话和问题类型的留出集，并报告分组结果与样本不确定性。

发布前，在仍运行的旧版本上，对冻结样本建立指向候选提交的真实 pre-switch anchor；切换后用同一数据集生成正式当前版本报告，通过后再调用既有 strict 激活流程。`real_query_gate.py:1151` 已要求该顺序。如果当前版本缺历史切换前基线，应在后续受控发布中建立真实链路，不能事后补造历史证据。
