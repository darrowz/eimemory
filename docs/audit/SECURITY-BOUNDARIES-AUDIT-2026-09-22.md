## 2. 架构结论

### 已观察到的良好边界

公开入口围绕 Runtime、MemoryAPI、RPC 与宿主适配器组织；存储、召回、控制和集成四个平面有明确的文档所有权。RuntimeStore 已存在 `mutate_records_atomically` 和 `mutate_capabilities_atomically` 等统一事务接口，记录/图/outbox 可以在同一 SQLite 提交中落地。独立证据目录使用单独只读连接，普通候选元数据不能直接取得人工审批权限。路由会绑定 exact scope、来源、记录、片段摘要并进行最终复核。

这些边界应保留。不能为降低延迟跳过权威记录复核、跨请求缓存未绑定版本的证据，或让学习结果直接成为执行权限。

### 实际仍存在的结构性问题

`promotion_manager` 同时承担门禁、适配器调用、候选状态、产物引用、生命周期事件与观察启动。已读非 code 路径中，产物应用、候选 rewrite、promotion record、watch 初始化是分开的操作；存在中断窗口。给外面套一个事务但内部继续调用自行 commit 的方法，不会产生真正的原子性。

RuntimeStore 持有同一个 RLock 和 SQLite 连接；已读写路径在提交后仍于锁内 flush JSONL/outbox 和导出 Markdown。数据库提交已结束，并不代表锁等待和磁盘工作已结束。未经版本协调就把导出搬到线程池，又可能让旧版本覆盖新版本。

### 本轮已实现的解耦

新增 `eimemory/core/strict_json.py`，只负责不可信传输 JSON 的字节/深度/重复键/非有限数校验，不依赖 Runtime、存储或治理。新增 `adapters/runtime/http_boundary.py`，只负责 HTTP framing、Bearer 比较和请求线程上限。客户端/服务端保留各自业务调度职责，不复制第二份 Runtime。

这是局部边界拆分，不是全项目架构重构完成。没有新建并行状态所有者、第二套审批库或隐式修复调度器。

### 建议的后续重构顺序（未实现）

先把晋升拆成纯 `PromotionPlan` 与 effect-owning executor；候选、artifact 引用、请求、观察计划、outbox 由一个事务所有者提交。涉及代码/部署等外部效果时，以预写 intent、期望前后摘要、幂等操作键和恢复状态机衔接，不能把文件系统和 SQLite 当成同一个事务。

其次建立与现有 exact scope/来源/摘要契约兼容的只读查询端口；测量后再决定 WAL 只读连接数量及读快照期限。导出工作使用持久 outbox、记录版本/CAS 和确定性顺序，释放写锁后执行，失败保留可恢复回执。

最后再依据完整 import 图决定其余模块拆分；不能只按文件行数拆模块，或用跨包私有方法转发掩盖原有耦合。

## 4. 业务闭环的真实状态

当前可确认的主流程是：输入/捕获 → 权威记录和投影 → 检索与证据组装 → 评价/治理 → 应用 → 观察/奖励/保留或回滚。文档描述完整流程，不代表每条入口、异常和重试分支已经闭合。

本轮关闭的是几个局部“把失败当成功”的判断：异常枚举不等于无冲突，缺健康不等于健康，非有限分数不等于达标，元数据回滚不等于产物撤销。审批满容量重试恢复幂等，但仍保留原有来源/审批检查。

尚未关闭的端到端工作包括：非 code 晋升多写入的崩溃窗口；孤儿产物/watch 对账；真正撤销和失败补偿；公共 outcome 的全入口幂等、奖励来源和历史迁移；实际健康证据的身份/时效绑定；调度超时后的副作用未知状态和租约回读。这些问题不能用“全部自动重试”“吞掉异常”“返回 ok”“默认健康 True”来修复。

建议发布恢复状态明确区分 `not_started`、`committed`、`effects_unknown`、`requires_reconciliation`。只有效果所有者证实目标摘要回到先前状态并且相关 ledger/观察状态一致，才能记录成功回滚。

## 5. 性能结论：没有给出未经实测的提升百分比

本轮有实证的是：失败日志不再无界读取；HEAD 解析不再等待本不应存在的正文；RPC 活请求线程数有界，拒绝请求不会留一个无界新 worker。日志测试使用大于 2 MB 的预存文件，并拦截读取参数，要求单次读取不超过 1024 字节的测试预算。生产默认日志预算仍为原有 256 KiB。

没有测量真实召回 p50/p95/p99、冷启动、真实模型往返、数据库规模曲线和宿主已交付成功率。没有声称 30%–50% 提升、所有请求三秒完成或已经满足三秒业务 SLA。当前源码出现 fast3s/assisted10s 延迟分层，本轮没有把它替换成统一三秒，没有修改 Luna/其他模型或推理参数。

后续性能验收应分别统计排队、锁等待、SQL、解码/摘要校验、候选融合、模型核验和宿主交付；按 exact scope、数据量、候选数、payload 大小与并发分层。正确证据且已交付、正确 no_evidence、不可用、晚到、错误引用必须分开计数。超时返回空结果不算性能修复成功。

H3 类只读连接/短写锁与长事务问题，只有在保持权威摘要、范围隔离、outbox 顺序及崩溃恢复不变的条件下才能优化。本包没有删除 fsync、跳过校验、增加答案缓存或盲目提高模型并发。

## 7. 发布阻断条件与操作风险

不应根据本包宣称项目已安全、L5 已达成或全量修复完成。将本包用于发布前，至少需要完成完整工作副本 canonical 预检；现有相关测试与新增测试；普通/attestation 凭据分离及重定向兼容性验证；32 线程/5 秒策略在真实负载下的错误率和有效完成率评估；晋升和回滚未关闭项的修复或明确禁用受影响自动应用路径。

修改只发生在用户选择的本地工作副本。即便 `git apply --check` 通过，多文件文件系统写入也不是跨文件崩溃原子事务。保留独立工作副本，不在生产目录直接打补丁；不要自动 reset/clean 原工作区。没有执行任何 GitHub 写操作、PR、推送或生产部署。
