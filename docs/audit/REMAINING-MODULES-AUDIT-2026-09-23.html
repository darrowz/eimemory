二、存储层审计（storage）

2.1 总体画像：基础工程扎实，检索路径防护不均

正面确认（逐行验证）：写路径的事务设计、outbox 模式、崩溃恢复与 digest 链均真实落地且逻辑正确；canonical_json 已全库统一（此前轮次报告的序列化不一致已修复）；payload_segments 大对象分片、atomic_file 原子写、maintenance 维护任务族达到高安全工程标准。但检索与导出路径上的防护密度明显低于写路径：校验、白名单、预算控制三类防护在 search/export/排序等读路径上要么缺失要么可被绕过。

2.2 高危问题

高危 · STO-1record_id 无字符校验 + 导出拼路径 → 路径遍历写

record_export.py:25 在导出记录时将 record_id 直接拼接进文件路径，而 record_id 自入库起无任何字符白名单校验（创建/导入路径均未过滤 ../、绝对路径、Windows 盘符等形态）。组合效果：能够控制 record_id 的写入方（含外部导入通道，见 MIS-3）可使导出文件落到任意可写目录，构成路径遍历写。已二次源码验证：导出路径构造处无 os.path.basename / 字符过滤 / 前缀锚定。

storage/record_export.py:25 · record_id 全链路无校验（创建/导入/导出三处）

修复建议：① record_id 入库前强制 ^[A-Za-z0-9_.-]+$ 白名单（拒绝即抛错，非静默清洗）；② 导出路径构造改为 export_dir / sanitize(record_id) 双保险，并断言解析后路径仍位于导出根目录内。两处均为小改动。
高危 · STO-2RuntimeStore.search() 无 deadline 包装，5+ 生产调用方绕过召回预算

存储层提供了带 deadline 的检索入口，但 RuntimeStore.search() 这一最常用的门面方法未做任何预算包装，直接透传到底层查询。已确认 5 个以上生产调用方经此入口发起检索，全部处于预算体系之外——这是"三入口不注入预算"（跨轮存活高危 #1）在存储层侧的镜像：入口侧不注入，存储侧也不强制，预算体系两头上悬空。图扩展的双重 N+1（跨轮存活高危 #8）同样经由无预算路径执行，deadline 完全无法约束。

storage/runtime_store.py（search 门面）· 5+ 生产调用方（api/memory.py 图扩展、knowledge、scheduler 等）

修复建议：RuntimeStore.search() 增加 deadline 参数并向下传播到底层游标/分页循环（超时即返回部分结果 + degraded 标记）；调用方审计清单一次跑齐，与入口侧预算注入（P1-6）同批落地。
高危 · STO-3FTS unicode61 分词器对中文无效 → 中文召回退化为 anchor LIKE 全表扫 + 递归重查双倍开销

FTS5 表使用默认 unicode61 分词器，按 Unicode 类别切词，对 CJK 文本不产生有效 token（中文整句通常被切成极少的大段或直接无命中）。逐行确认退化链路：中文查询 FTS 命中为空 → 框架将其解释为"无结果"并回退到 anchor 字段 LIKE 全表扫描 → 空结果再触发递归重查（同词重扫一次）。对中文用户（本项目的核心使用场景），每次召回都走最慢路径且重复执行两次，叠加单连接 + 全局 RLock 串行（跨轮存活高危 #9），直接威胁 3 秒召回硬指标。英文/混合内容不受影响，因此基准测试（多为英文语料）无法暴露此问题。

storage/sqlite_store.py（FTS 建表与查询回退逻辑）

修复建议：三选一按成本递增：① FTS 分词器改 trigram（SQLite 3.34+ 内置，建表语句改动一行 + 重建索引）；② 中文 anchor 字段建独立倒排/前缀索引；③ 最低成本先移除"空结果递归重查"（双倍开销白付，无收益）。修复后必须用纯中文语料重跑召回基准。

2.3 中危问题

中危 · STO-4_allowed_order_by 的 endswith 回退削弱排序白名单

排序字段白名单函数在精确匹配失败后存在 endswith 回退逻辑（如传入 x.created_at 可命中白名单中的 created_at）。这不是当前可利用的注入（值仍被限定在白名单后缀集合内），但白名单语义从"全等匹配"被弱化为"后缀匹配"，未来白名单扩充时可能意外放行带表名前缀的歧义字段。ORDER BY 注入面在 SQLite 参数化查询下本已封闭，此回退属于纵深防御上的非必要松动。

storage/sqlite_store.py（_allowed_order_by）

修复建议：删除 endswith 回退，改为显式剥离表前缀后精确匹配；或白名单同时收录带前缀形态。一行改动。
中危 · STO-5外部 21 处越界访问 store._lock / sqlite.conn

全库 21 处（storage 包之外）直接访问存储层私有锁 store._lock 与裸连接 store.sqlite.conn，含若干无锁查询（部分经 getattr 动态绕过，grep 静态扫描会漏报）。这使 storage 层任何内部重构（锁升级为读写锁、连接池化——恰是修复高危 #9 必需的改动）都会静默破坏外部调用方。与 governance 审计发现的 8 处裸连接直访同源，但范围更大、且分布在更多包。

21 处，分布于 api / knowledge / scheduler / capabilities / adapters 等（含 getattr 绕过形态）

修复建议：storage 层补一组带锁只读查询公共 API（with_store_connection 上下文管理器即可），外部 21 处一次性迁移；迁移完成前先加运行时 deprecation 警告定位存量调用。

2.4 跨轮存活项复验：jsonl 重复段与单连接串行

jsonl.py 整段重复：本轮整体复验 DRIFT = 27 / 925 行。对重复区段做逐行 diff，925 行重复体中已有 27 行两侧不一致（一侧修了 bug / 改了签名，另一侧未跟）——即"复制粘贴双份"已经开始独立漂移，每多漂移一行，未来删除重复段的成本就上升一分。注意：本轮存储组代理曾报告"类体 0 漂移"，与本轮整体逐行比对结果（27 行）不一致，本报告以覆盖完整区段的逐行 diff 复验为准。这与第三轮审计结论（27 行漂移）吻合。

单连接 + 全局 RLock 串行：复验仍在。所有读写共享一个 SQLite 连接与一把进程级 RLock，32 worker 并发场景下吞吐恒等于单线程。该架构与 STO-3（中文全表扫）叠加时最危险：一个慢查询持锁，全进程召回排队。修复 STO-5（外部越界访问）是引入读写分离连接的前置条件。

三、召回层审计（retrieval）

3.1 总体画像：上一轮修复真实落地，注入面出现新缺口

正面确认：① get_by_exact_refs 批量水合接口已真实落地且三处调用方全部接线（此前轮次报告的"接口不存在/死代码引用"已修复）；② fusion 排序 key 已改为确定性实现（不再依赖字典序不稳定来源）；③ TEI / embedding 外呼的网络边界防护完备（超时、重试上限、错误隔离齐全）。但渲染侧出现新的防护缺口：同为"记忆内容进入宿主 prompt"的路径，proactive 链路有 untrusted 包裹，loadout 链路没有——防护是按路径逐个手工加的，而非按数据流系统性铺设，这正是缺口反复出现的原因。

3.2 高危问题

高危 · REC-1loadout 渲染无 untrusted 包裹 —— 记忆到宿主 prompt 的最短注入路径

recall/loadout.py:111-115 渲染 loadout（召回结果注入宿主上下文的载体）时，直接把记忆内容拼入输出，未调用 untrusted 包裹工具；对照同模块 proactive 路径（有包裹），确认这是遗漏而非设计。攻击链：任何污染记忆的写入方（外部导入双通道 MIS-3、注入检测只有 8 个英文短语黑名单的 MIS-4、或被投毒的 embedding 源）→ 记忆入库 → 召回命中 → loadout 渲染 → 内容以"可信记忆"身份进入宿主 LLM prompt，可携带"忽略此前指令"类指令。这是全程环节最少、防护最少的一条记忆注入路径。

retrieval/recall/loadout.py:111-115 · 对照：proactive 路径已有包裹

修复建议：① 立即在 loadout 渲染处加与 proactive 相同的 untrusted 包裹（约 5 行改动，P0）；② 根治方案是把"渲染进宿主 prompt"收敛为唯一函数、唯一包裹点，杜绝按路径手工加防护的模式。

3.3 中危问题

中危 · REC-2caller_assistance 子进程全量继承父进程环境变量

llm/command_client.py:103-104 启动子进程时未做环境最小化，子进程全量继承父环境——父进程中的 API key、token、内网代理配置全部进入子进程上下文。与 governance 审计发现的 v1 验证环境全量继承（含 secret）同模式，说明这是跨模块的系统性疏忽而非孤例。子进程执行的命令由 caller-assisted 验证流程动态决定，攻击面虽需特定前置条件，但最小权限原则下不应存在。

llm/command_client.py:103-104

修复建议：子进程环境改为显式白名单构造（PATH + 必需变量），与 v1 验证环境最小化（跨轮高危 #5 修复项）合并为同一个 infra 工单。
中危 · REC-3sqlite_source 的 result_limit==1 identity 短路，与 postgres 路径语义相反

sqlite_source 在 _result_limit == 1 时存在直接返回首个候选的 identity 短路；而 postgres 路径（RET-08，evaluation 审计已确认）对 limit=1 保持完整评分排序。两条后端对同一查询给出不同语义：sqlite 直接取候选集第一个（可能是未排序的存储序），postgres 取评分最高者。同库不同后端结果不一致，会让"换后端"变成行为变更，也让基于 sqlite 的评测结论无法外推。

retrieval/sqlite_source.py（_result_limit==1 分支）

修复建议：删除 identity 短路（limit=1 走完整排序取 top-1）；若短路是为性能，应改为排序后截断并注明。
中危 · REC-4_RECALL_DOC_CACHE 无锁 LRU，并发下状态不确定

召回文档缓存为模块级 dict 手工实现 LRU，无锁保护。多线程（RPC worker、scheduler 线程）并发读写时存在脏读与容量失守（驱逐计数竞态），最坏情况缓存无限增长或返回半更新条目。非崩溃级缺陷，但发生在最热路径上，且一旦未来加多线程入口会立即放大。

retrieval（_RECALL_DOC_CACHE 实现处）

修复建议：替换为 functools.lru_cache 或加锁；注意若模块级可变全局被治理规则禁止，应移入 runtime 持有。改动约 10 行。

回调注册表共 37 个以 _ 开头的私有回调，其中 2 个在声明清单中缺失但存在调用点——回调框架对私有回调的声明约束不完整，重构时极易漏改。属工程卫生问题，与 governance 的 6 死符号同类。

四、API / CLI / Adapters 集成层审计

4.1 总体画像：观测已部分下沉，执行路径仍在绕行

正面确认：三入口（CLI/RPC/SDK）的 watch 观测逻辑已部分下沉到公共层，不再完全依赖各入口自觉调用；get_by_exact_refs 等新接口在 API 层接线完整。但执行路径（outcome 记录）发现了比观测路径更严重的绕行：一个 adapter 通道直调底层函数绕过 Runtime 统一入口，导致下游全部观测与晋升逻辑对该通道失明——这是本轮最重要的单点发现。

4.2 高危问题

高危 · INT-1adapter.record_terminal 绕过 Runtime.record_outcome —— promotion watch 对 codex / hermes 通道系统性失明

adapters/runtime/service.py:1418-1436 的 record_terminal（codex / hermes 两个生产通道的会话终止钩子）直接调用 record_terminal_bundle，而非统一入口 Runtime.record_outcome。二次源码验证（调用链唯一性确认）：record_outcome_observations——晋升观察数据的写入函数——全库唯一调用点是 api/runtime.py:2441（即 Runtime.record_outcome 内部）。因此经 codex / hermes 通道产生的所有会话结果从不进入晋升观察数据：promotion watch 拿不到这两条通道的 outcome 样本，基于 outcome 的评估、reward 信号、能力升降全部对这两个通道失明。

这不是低频边角：codex 与 hermes 是生产 IM 通道。其后果是晋升评估的样本分布被系统性截断——只包含其他通道的会话，得出的"模式有效/无效"结论对失明通道不成立甚至相反。与 reward 仅 CLI 触发（跨轮存活高危 #4）合并看：生产流量的 outcome 闭环存在多条断链，且断链方式各异（有的少触发点、有的绕入口），说明闭环完整性缺乏"入口唯一性"这层结构性保障。

adapters/runtime/service.py:1418-1436 · 唯一调用点验证：api/runtime.py:2441

5.2 高危问题

高危 · MIS-1研究闭环 model review 三重断链：review 永远不会发生

intake/closure_review.py 的模型复核（model review）流程存在三重断链，已逐一二次源码验证：

  • 断链一（状态字段写读不一致）：retry 路径（closure_review.py:201）写入的状态值是 "pending"，而消费方判定条件（:140）要求 "pending_model_review"——retry 过的记录永远不满足消费条件，直接掉出流程。
  • 断链二（meta / content 双轨错位）：retry 只更新 content 字段不改 meta，而消费方优先读 meta——即使状态值改对了，消费方读到的仍是旧 meta，判定依旧失败。
  • 断链三（函数死代码）：retry 函数本身无任何调度消费方（死代码），review 函数同样无调度入口——即使前两链修复，也没有任何东西会周期性触发 review。

三重断链叠加的含义是：研究闭环的"模型复核"环节在当前代码状态下永远不会执行，且因为 retry 的死代码性质，连"试图触发然后失败"的痕迹都不会留下——静默缺失，监控不可见。这是"已写出未接线"模式最完整的标本：状态机、字段、调度三层各断一处，单看每层都"差不多对"。

intake/closure_review.py:201（retry 写入）· :140（消费判定）· retry/review 函数定义与调度入口

修复建议：状态常量收敛为单一枚举模块（写读共源）；retry 同时更新 meta 与 content；给 review 加调度入口（scheduler 已有成熟 cron 机制）。修复后必须补一条端到端测试：retry → 调度 → review 真实发生。
高危 · MIS-2knowledge refresh 写事务内全表扫描 ×2 + 25MB PDF 文件 I/O，长期持锁阻塞全库写入

knowledge 的 refresh 流程在单个写事务内部执行两次全表扫描，并在事务内同步读取最大约 25MB 的 PDF 文件做解析——文件 I/O 与重计算全部发生在持有写锁期间。在单连接 + 全局 RLock 架构（跨轮高危 #9）下，refresh 运行期间整个进程的所有记忆读写全部排队；若 PDF 位于慢速磁盘或网络挂载，一次 refresh 可把召回硬指标（3s）拖穿到分钟级。这解释了任何"偶发全系统卡顿"类现象的最可能来源。

修复建议：refresh 改三段式：事务外读取+解析（只读）→ 事务内批量提交（短事务）→ 事务外后处理；全表扫描改分页游标。改造后用 25MB 样本 PDF 实测写锁持有时长 < 1s。
高危 · MIS-3外部导入双通道无筛查：intake/packs.py 与 compatibility/migration_helpers.py

两条外部数据导入通道均无内容筛查：① intake/packs.py 导入研究 pack 时不做注入/污染检查直接入库；② compatibility/migration_helpers.py 迁移导入同样直通。结合 REC-1（loadout 无包裹）与 MIS-4（注入检测本身薄弱），构成完整攻击链的入口段：恶意内容可经导入通道入库 → 召回命中 → 无标记直达宿主 prompt。与 STO-1（record_id 无校验）叠加，导入通道连"标识符形态"的约束都没有。

七、三个全新高危专题

7.1 INT-1：record_terminal 绕行 —— 闭环缺"入口唯一性"保障

调用链对比（二次验证后还原）：

  • 设计路径：adapter → Runtime.record_outcome（api/runtime.py）→ 记录 outcome → 写 record_outcome_observations（:2441）→ promotion watch 消费 → 能力评估/reward。
  • 实际路径（codex/hermes）：adapter → record_terminal_bundle（直调底层）→ 记录写入了，observations 未写，watch 永远看不见。

影响面评估：失明的不只是 watch——凡是挂在 record_outcome 之后的下游（outcome 评估、能力升降样本、reward 信号、双写恢复）对这两条通道全部无效。更关键的是统计偏差是静默的：晋升报告不会报错，只会基于残缺样本给出"看似正常"的结论。根因不在这一处代码，而在架构没有"outcome 写入唯一入口"的约束——Runtime 入口存在，但没有任何机制阻止绕行。同类绕行在 reward（跨轮 #4，触发点缺失型）与 closure_review（MIS-1，状态机断链型）以不同形态反复出现，说明需要的是结构性方案而非逐处补丁：核心写入口收敛 + CI 层禁止 adapters/intake 直接调用底层写函数。

7.2 MIS-1：三重断链的解剖 —— 为什么四轮审计才抓到它

closure_review 的三重断链每一重单独看都是"小问题"：状态值差一个词、meta 没同步、函数没调度。静态扫描抓不到（字段值都是合法字符串、函数语法完整）、单测抓不到（每个函数单独测都能过）、集成测试抓不到（需要 retry → 调度 → review 的全链路串联才暴露）。只有把"研究闭环"当作端到端业务流逐环验证状态机转换，才能发现 review 环节从未点亮。这提示验收方法论的改进方向：为每条业务闭环画状态机图，逐条边验证"存在真实代码使状态从 A 到 B"，而不是逐函数验证（详见第十章）。

7.3 STO-1：路径遍历写的攻击面与最小修复

攻击前提：攻击者需能控制一条记录的 record_id。当前可达成路径：外部导入双通道（MIS-3，无筛查）；未来任何开放写入接口。攻击效果：导出操作触发时文件写到任意可写路径（可覆盖配置、写启动项，取决于运行身份）。风险定级说明：虽然当前部署形态下控制 record_id 的门槛不低，但"标识符无校验 + 路径拼接"的组合在安全工程上属于必须修复的缺陷——它的存在使 MIS-3（导入无筛查）从"内容污染"升级为"任意文件写"。修复成本极低（两处小改动）是它进入 P0 的原因：性价比最高的安全修复。

八、"已写出未接线"模式（第四批）与正面确认

8.1 第四批实例与模式共性

四轮审计累计确认的"已写出未接线"实例：第一批（governance）check_promotion_watch_orphans、requires_reconciliation 无外部消费方；第二批（evaluation）verdict 永远 not_run、longmemeval 7 处静默吞没；第三批（第三轮）memory_rule watch 双断链、_effects_unknown_after_timeout；本批retry_unavailable_research_closures（MIS-1 断链三）、capability_v3_backfill 默认关闭（MIS-7）。

模式共性：① 功能实现完整（函数、状态机、数据结构都在），缺的是最后一米——调用点、默认值、调度入口；② 缺失方式各不相同，说明不是某个人的疏忽，而是代码合入流程缺少"新功能必须有消费方"的验证环节；③ 危害形态统一为静默失效——不报错、不告警、监控盲区，只能靠审计或用户发现业务没发生。系统性根治建议：建立"接线清单"制度——每个新模块合入时声明其触发入口（谁调用/何时调度），CI 校验声明与实际调用图一致；对存量六批实例逐一裁决"接线或删除"，禁止中间态。这与第三轮提出的拆分方案第一批（删死代码）应合并执行。

8.2 正面确认（本轮独立验证）

  • 安全工程高标准组件：payload_segments（大对象分片）、atomic_file（原子写）、maintenance（维护任务族）、safe_transport（安全外呼封装）、papers artifacts、seed_manifest——超时、原子性、错误隔离设计完备，可作为全库其他模块的对齐范本。
  • contracts/core 公共下沉层真实生效：core 公共层被 70+ 文件引用，此前轮次担心的"公共层空转"未发生；get_by_exact_refs 批量水合接口三处接线全部落地，第三轮报告的"死代码引用"已修复。
  • 召回层确定性收敛：fusion 排序 key 确定性化、TEI/embedding 外呼边界防护完备、proactive 路径 untrusted 包裹正确——问题只在 loadout 一处的遗漏（REC-1），整体防护意识是有的。
  • 存储写路径质量：事务、outbox、崩溃恢复、digest 链、canonical_json 统一，全部逐行验证成立——写路径的工程质量显著高于读路径，修复方向明确（把读路径拉齐）。

十、验收建议

  • 闭环验收用"状态机逐边验证"而非逐函数测试：对研究闭环、晋升闭环、reward 闭环各画一张状态机图，逐条边断言"存在真实代码 + 真实调度使该转换发生"。MIS-1 这类三重断链只有此方法可测。
  • 性能验收必须含中文语料：STO-3 说明英文基准对中文场景零代表性。建立固定中文召回基准集，每次存储层改动重跑；3s 指标以中文基准为准。
  • 安全验收加"恶意 record_id / 恶意导入包"两组红队用例：路径遍历（STO-1）与导入投毒（MIS-3）各建 10 条攻击样本入 CI。
  • CI 静态守卫（一次性建设，长期收益）：① 禁止 adapters/intake 直接 import 底层写函数（防 INT-1 复发）；② 禁止裸 urlopen；③ 禁止跨包 import 下划线私有函数（防 MIS-4 复发）；④ 旧注册表符号清零校验；⑤ 新功能"接线声明"校验（防第五批未接线）。
  • 修复验证一律走"宣称 vs 落地"双查：第三轮曾出现 4 项"宣称修复未生效"（死代码对账等），本轮复验 jsonl 漂移时又出现组内代理与全量比对结果不一致——修复验证不能采信宣称，必须以源码 grep / e2e 行为为准。
