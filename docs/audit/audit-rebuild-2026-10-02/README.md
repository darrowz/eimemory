## 四条工作线

四线是同一模块上的协作工作流，不是把仓库切成四个模块：

1. **源码审计**：逐模块读取源码，沿数据流、事务、错误与恢复路径记录可复核证据；明确已读文件、未读范围和仍待验证的假设
2. **缺陷修复**：对确认的问题做最小修复与回归测试，保存失败复现、修复内容和测试结果；不将推测直接当成缺陷
3. **独立复核**：独立检查模块与修复，覆盖异常、回滚、资源清理和重复调用等路径；保留两次独立源码审查的明确覆盖范围
4. **安全精简**：识别重复实现、无效复杂度和可安全缩小的改动；保留行为、兼容性、数据与证据，未经证实不删除

首个模块为 `eimemory/storage` 的普通事务与资源生命周期。后续模块顺序按数据丢失风险、依赖关系与实证结果决定，逐批登记，不把未审模块提前算入覆盖率。

## 小批次保存与验收

- 每个批次限定模块/文件/问题，保留基线和变更后的源码标识
- 台账记录审计、独立复核、发现、修复和测试的证据；缺少记录的文件始终视为未审
- 图解析、计划文档和历史审计记录不折算成本轮源码审计进度
- 修复须附对应回归与适用的项目检查；通过、失败、受阻、未运行分开报告
- 验证完成的小批次及时提交到本分支，再读取远端提交与文件内容确认已保存
- 每次更新保留既有历史；不改写历史，不推送 `master`，不合并或部署

## 提交机制

使用仓库现有授权连接，先读取分支 HEAD 和父提交 tree；把本批次文件写为 Git blobs，在父 tree 上创建新 tree，再创建以刚核对 HEAD 为唯一父提交的 commit。整个多文件批次通过一次非强制 fast-forward 更新分支引用发布，因此不会逐文件暴露半个批次。

连接器没有 `expected_old_sha` 参数，不能宣称严格 compare-and-swap。采用单写入者串行发布，在更新前再次核对 HEAD，更新后再次读取远端引用、提交 tree 和文件内容；若 HEAD 发生意外变化，停止并协调，绝不使用 force。非快进更新被拒绝时保留待发布批次，重新核对后处理。
