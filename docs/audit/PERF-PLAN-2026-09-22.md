## 0. 执行摘要

**不使用** `docs/audit/l5-v3-performance-baseline.md` 的旧数据——该文档自述「captured before the v3 storage work … must be recaptured」，已失效。本方案改用本机实测复现。

**核心结论**：recall 热路径存在**结构性放大**。单次 recall 产生 **4,098 条 SQL 语句**，其中 **2,002 条为 FTS `docsize` 查询**。根因是词法臂 `_collect_fts_candidates`（`sqlite_store.py:4611-4618`）使用 `bm25()` + `ORDER BY bm25_score ASC, quality_score DESC, updated_at DESC`：

- `bm25()` 为**每一行**匹配结果读取 docsize（实测 2,000 次单独读取 = **785.8 ms**）；
- 复合 `ORDER BY` 使 `LIMIT` **完全失去剪枝能力**（查询计划：`SCAN recall_index_fts` + `USE TEMP B-TREE FOR ORDER BY`）。

### 重要修正（反例验证结果）

本方案初稿曾建议「改用 `ORDER BY rank` 替代 `bm25()`，零语义风险」。**实测证明该结论错误**，必须记录：

| 实验 | 结果 |
| --- | --- |
| 真实过滤器下 `ORDER BY rank` vs 现状 | **1.0×（无收益）**——复合排序键仍需 TEMP B-TREE |
| `ORDER BY rank`（去掉次排序键）结果集 | **与现状不同**（uniform 与 varied 语料均 `identical: False`） |
| 有界内层子查询（`LIMIT 250` 后复合排序） | **结果集也不同**（`identical: False`） |

**原因**：FTS5 `rank` 在真实语料中**大量并列**——实测 300 篇文档仅 40 个不同 rank 值，**top-10 全部同分**。此时 `quality_score`/`updated_at` 次排序键**才是决定 top-N 的实际依据**，任何按 `rank` 的预剪枝都会改变结果。

**因此**：P0 不再是「换排序函数」，而是**先建立安全网，再谈优化**（见 §2）。这是一个诚实但价值更高的结论。

## 2. P0：先建安全网，再优化（前置条件）

> **结论**：在**当前排序语义被测试锁死之前**，任何词法臂裁剪都是不可安全合入的。P0 不是性能改动，而是**为后续优化建立可判定的等价性基线**。

### 2.1 为什么必须先做

`_collect_fts_candidates` 的 top-`limit` 窗口由**三个键联合决定**（rank → quality_score → updated_at）。而 `rank` 在真实语料中高度并列（实测 top-10 全部同分），因此**次排序键才是实际胜出依据**。这意味着：

- 任何「按 rank 取前 K 再排序」的方案都等价于**丢弃了次排序键的候选**；
- 要安全优化，必须**首先**明确并固化「top-N 的权威定义」。

### 2.2 安全网改法

**新增等价性测试**（`tests/test_recall_perf_bounds.py`）：

```python
def test_fts_topn_is_stable_under_varied_tiebreaks(tmp_path) -> None:
    """BASELINE: 固化 FTS top-N 的权威排序语义（rank → quality → updated_at）。

    此测试是后续性能优化的等价性锚点：任何词法臂改写都必须与它一致。
    """
    store = RuntimeStore(tmp_path)
    for i in range(200):
        store.append(_memory(f"alpha deployment marker {i}"))
    with store._lock:
        # 制造真实的并列 + 不同次排序键
        store.sqlite.conn.execute(
            "UPDATE recall_index SET quality_score = 0.5 + (rowid % 30) * 0.01,"
            " updated_at = '2026-01-' || printf('%02d', 1 + (rowid % 28)) || 'T00:00:00Z'"
        )
        where, params = store.sqlite._recall_index_where(
            kinds=["memory"], scope=SCOPE, recall_filters={}, alias="i"
        )
        sql = (
            "SELECT i.storage_key FROM recall_index_fts"
            " JOIN recall_index i ON i.storage_key = recall_index_fts.storage_key"
            " WHERE recall_index_fts MATCH ? AND " + " AND ".join(where)
            + " ORDER BY bm25(recall_index_fts) ASC, i.quality_score DESC, i.updated_at DESC LIMIT 5"
        )
        got = [r["storage_key"] for r in store.sqlite.conn.execute(sql, ["alpha", *params]).fetchall()]
    assert len(got) == 5
    # 记录权威结果（实现变更时必须与本快照一致）
    assert got == _FTS_TOPN_SNAPSHOT, "FTS top-5 ordering changed"
    store.close()
```

`_FTS_TOPN_SNAPSHOT` 在首次运行时回填（`u64`/摘要亦可），此后成为回归锚点。

**同时新增并列感知断言**，防止未来误判：

```python
def test_fts_rank_has_real_ties(tmp_path) -> None:
    """DOC: 真实语料下 rank 大量并列——次排序键才是 top-N 实际依据。"""
    ...  # 断言 distinct(rank) < n，证明并列存在
```

### 2.3 为何这是 P0 而非可选项

没有此锚点，§4 之后的任何词法优化都无法判断「是否改变了召回结果」。这是**所有后续性能工作的前置条件**。

## 3. P1：低风险、结果等价的优化

以下两项**不改变召回结果**，可安全并行推进。

### 3.1 消除热路径 schema 内省

**现象**：单次 recall 出现 **6× `PRAGMA index_list(recall_index)`** + **4× `PRAGMA table_info(recall_index)`** + **4× `SELECT 1 FROM recall_index LIMIT 1`**。

**改法**（`eimemory/storage/sqlite_store.py`）：

```python
def _ensure_recall_schema_once(self, *, force: bool = False) -> None:
    """Schema 兼容性检查每连接只做一次（PERF：消除热路径 PRAGMA）。"""
    if not force and getattr(self, "_recall_schema_verified", False):
        return
    self._prepare_deferred_recall_schema()
    self._ensure_recall_index_columns()
    self._recall_schema_verified = True
```

**约束**：写路径（`upsert`/`rewrite`/`DELETE`）与迁移路径**必须** `force=True` 或直接调用原子方法，因为它们可能改变 schema。建议在 `_create_indexes`、迁移入口显式 `force=True`。

**验证**：新增测试断言单次 recall 的 `PRAGMA` 语句数 ≤ 2，且写路径仍触发校验。

### 3.2 污染门纯函数记忆化（PERF-04）

**证据**：cProfile 显示 `_apply_online_recall_pollution_gate` 占 **0.70s / 2.14s（33%）**，其中 `build_recall_index_document` 被调用 **680 次 = 0.61s**。

**依据**：`build_recall_index_document(record)` 是**纯函数**（`recall/indexing.py:235`，仅依赖 `record` 的字段）。

**改法**：按稳定身份记忆化，注意失效：

```python
# eimemory/api/memory.py
from functools import lru_cache

@lru_cache(maxsize=4096)
def _recall_index_doc_cached(record_id: str, updated_at: str, _doc_key: str):
    """缓存维度 = 记录的『内容版本』；updated_at 变化即自动失效。"""
    ...  # 内部仍调用 build_recall_index_document
```

**约束**：
- 缓存键**必须**含 `updated_at`（或等价版本标记），否则记录更新后会读到陈旧分类；
- 需设内存上界（`maxsize`），避免无界增长。

**验证**：断言同一 recall 内 `build_recall_index_document` 实际计算次数 **≤ 唯一记录数**；并断言记录 `updated_at` 变更后取到新值。

## 4. P2：需谨慎评估的词法臂优化

> **前置**：§2 安全网必须已合入，且 §4 的每项都需经质量门（`p_at_3` / `noise_rate`）验证。

### 4.1 已排除的方案（记录以免重蹈）

| 方案 | 排除原因 |
| --- | --- |
| `ORDER BY rank` 替换 `bm25()` | 真实过滤器下无收益（复合排序仍需 TEMP B-TREE） |
| `ORDER BY rank` 单键 | **改变 top-N 结果**（并列下丢失次排序键依据） |
| 有界内层 `LIMIT K` 预剪枝 | **改变 top-N 结果**（同因） |
| 去掉 `ORDER BY` | 顺序未定义 |

### 4.2 待评估：先按次排序键分流并列组

**思路**：`rank` 并列是实现层面的必然（实测 top-10 全并列）。若绝大多数记录的次排序键区分度足够，可**先用索引把次排序键的候选序拉出**，再在**并列组内**用 rank 排序。

```sql
-- 思路示意：先取次排序键最优的一批，再在批内按 rank 排序
SELECT storage_key, quality_score, updated_at, bm25(recall_index_fts) AS s
FROM recall_index_fts
JOIN recall_index i ON i.storage_key = recall_index_fts.storage_key
WHERE recall_index_fts MATCH ? AND <filters>
  AND (i.quality_score, i.updated_at) >= (?, ?)      -- 次排序键下界，可走索引
ORDER BY s ASC, i.quality_score DESC, i.updated_at DESC
LIMIT ?
```

**可行性未知**，须实测：
1. 次排序键下界的选取（取第 K 优 `quality_score`）会漏掉「rank 显著更优但 quality 略低」的候选 —— **可能改变结果**；
2. 仅当 rank 分布高度并列时，该漏失才可接受。

**门槛**：须先在真实语料上量化「top-N 中 rank 并列比例」，若并列比例低，则不应采用。**未验证前不得实现**。

### 4.3 待评估：高频词剪枝（PERF-06）

**依据**：`fts5vocab` **可用**（已实测）。本机语料中 `deployment` 等词 df = 100%。

**风险**：**改变召回集合**，属语义变更。必须：
- opt-in（环境开关，默认关）；
- 由质量门（`p_at_3` / `noise_rate`）保护；
- 不得硬编码 stopword 表，须基于 `df/total` 动态判定。

### 4.4 其他

| ID | 问题 | 改法 | 备注 |
| --- | --- | --- | --- |
| **PERF-05** | 超宽索引 `idx_recall_index_scope_source_updated`（**12 列**） | 拆为窄索引：`(t,a,w,u,source_id,updated_at DESC)` + `(t,a,w,u,lane,visibility)` | 降低写放大与 WAL 体积；需迁移与索引校验测试 |

## 5. P2：修复批量 hydrate 死代码（RET-07）

### 5.1 现象

`eimemory/retrieval/engine.py:2345 _hydrate_records_batch` docstring 声明「prefer one batched exact-ref lookup when the store supports it」并检测 `get_by_exact_refs`：

```python
batch_fn = getattr(self.store, "get_by_exact_refs", None)
if callable(batch_fn):
    found = batch_fn(refs) or []
else:
    for record in records:          # ← 实际永远走这里
        item = self.store.get_by_exact_ref(...)
```

**但全库 `def get_by_exact_refs` 零命中**——方法**从未实现**，批量分支是**死代码**。

### 5.2 改法

实现缺失方法（`eimemory/storage/sqlite_store.py`，与 `get_by_exact_ref` 同语义）：

```python
def get_by_exact_refs(self, refs: list[dict], *, chunk_size: int = 100) -> list[RecordEnvelope]:
    """RET-07: 单语句批量精确 hydrate，替代逐条 get_by_exact_ref。

    分批以避免 SQLite 变量上限（默认 999）与查询计划退化。
    """
    self.assert_connection_lock_held()
    out: list[RecordEnvelope] = []
    for start in range(0, len(refs), chunk_size):
        chunk = refs[start:start + chunk_size]
        clauses, params = [], []
        for ref in chunk:
            scope = ref["scope"]
            clauses.append(
                "(record_id = ? AND tenant_id = ? AND agent_id = ? AND workspace_id = ?"
                " AND user_id = ? AND source_id = ?)"
            )
            params.extend([
                str(ref["record_id"] or "").strip(),
                scope.tenant_id or "default", scope.agent_id,
                scope.workspace_id, scope.user_id,
                normalize_source_id(ref["source_id"]),
            ])
        rows = self.conn.execute(
            "SELECT record_id, kind, status, tenant_id, agent_id, workspace_id, user_id,"
            " source_id, payload_json, payload_pointer_json, payload_digest"
            " FROM records WHERE " + " OR ".join(clauses),
            params,
        ).fetchall()
        for row in rows:
            record = self._record_from_storage_row(row, hydrate=True)
            if record is not None and self._record_matches_projection_row(record, row):
                out.append(record)
    return out
```

并在 `RuntimeStore` 侧暴露同名委托方法（`runtime_store.py`，参照 `get_by_exact_ref:946`）。

**降级选项**：若暂不实现，应**移除死代码分支**并注明，避免「看似已批量、实为 N+1」的误导。

**注意**：本机实测默认 recall 下 `get_by_exact_ref` 调用数为 **0**（主查询走 FTS 单语句路径），故该项主要受益于 **admission / 大批量变更校验**场景，而非默认 recall。
