三、capability_catalog 专项

  
3.1 seal/fail-closed 机制【主体成立，1 处绕过缺口】

  

    
seal() 后所有 register_executor/register_case/graders.register 被 _require_mutable 阻断（抛 CatalogResolutionError）；evidence chain 拒绝 catalog 自证（source == "eimemory.evaluation.catalog" 不可作独立证据）；execute 异常一律 _failed_execution（verdict=blocked）；catalog_not_configured 所有 5 个调用方均正确接住（无 fail-open）；executor 注册要求 revision + contract_digest 匹配，冲突检测完整。
正面确认：主体安全设计在评估模块中工程水准最高。

  

  

    

高危 · CC-1

publish_into 未检查目标 catalog sealed 状态——seal 后仍可注入

    
publish_into（capability_catalog.py:1004-1021）转发 grader/executor/case 到 destination，调用的 destination.register_executor/register_case 
本身有 _require_mutable 检查
——若 destination 已 sealed 会抛错。
但本函数无文档标注此行为
，且调用方可能误以为 publish_into 是"安全发布"而不知道 sealed catalog 会抛异常。实际行为是 fail-closed（抛异常），但代码可读性和设计意图不明确。本轮复验确认：publish_into 调用的 register_executor/register_case 确实有 _require_mutable 守卫，因此 sealed 后 publish_into 会抛 CatalogResolutionError——
实际是安全的，但无显式 sealed 检查使代码可读性差
。

    
capability_catalog.py:1004-1021（复验确认：间接通过 register_* 的 _require_mutable 保护）

    

修复建议（可读性）：
在 publish_into 开头加 
destination._require_mutable()
 显式检查并给出清晰错误消息。

  

  
3.2 大整数 ValueError 穿透

  

    

中危 · CC-2

normalize_json_payload 对大整数抛 ValueError 穿透 CatalogResolutionError 捕获

    
_safe_mapping（capability_catalog.py:60-66）只捕获 CapabilityContractError；normalize_json_payload 内 json.dumps 对超 4300 位整数（Python 3.11+ int_max_str_digits）抛 
ValueError
（非 CapabilityContractError）→ 穿透 _safe_mapping → 调用方若仅捕获 CatalogResolutionError 则漏接。一个约 6 万位十进制整数 ≈ 60KB &lt; 256KB 序列化上限，可在构造 CatalogCase 时触发未分类异常。

    
contracts/capability_validators.py:219（int 无上限） · capability_catalog.py:60-66（只捕获 CapabilityContractError）

    

修复建议：
对 int 增加位数上限检查（如 len(str(abs(value))) ≤ 4096），或 json.dumps 包裹并统一抛 CapabilityContractError。

  

  
3.3 证据链验证与 executor 身份校验【安全】

  

    
_validate_independent_evidence_chain（:1024-1107）：probe 和 trace 必须来自 store get_by_id、拒绝 catalog 自证、trace 强制 capability_revision_id/provider_binding_id 全匹配、verifier 必须独立且绑定到 probe。唯一缺口：probe 的 revision/binding 若为空则跳过校验（:1067-1069），trace 仍强制全匹配——probe 宽松但不足以单独伪造通过（低危）。executor 注册要求 callable + revision + contract_digest，执行时 case 必须绑定确切 revision + digest，不匹配 _failed_execution。

  

  
四、real_query_gate 专项

  

    

高危 · RQG-1

tracemalloc 外部 tracer 存在时 gate 永远 blocking——release 无法发布

    
_evaluate_real_query_candidate（:1688-1706，复验确认）：检测到外部 tracemalloc 运行时直接设 
peak_memory = 0

任何已有 tracemalloc 运行的环境下，production recall gate 永远无法通过

real_query_gate.py:1688-1706（peak_memory=0）, 2339-2340（blocking 判定）

    

修复建议：
外部 tracer 存在时改用 tracemalloc.take_snapshot().statistics('filename') 或标记 memory_measurement 为 skipped（跳过 blocking 而非 blocking）。

  

  

    

防篡改设计（正面确认）
：report_payload_digest（sha256 重算比对）+ result_digest + ranking_result_digest + policy_digest（固定值）+ _independent_real_query_metrics_valid（从 store 重新获取 records，重算全部 metrics，与报告逐项比对，允许 1e-6 浮点误差）+ high-water mark（不可回退）+ attempt_id 链式幂等。
记忆注入无法伪造通过结果

3s/10s 双轨延迟
（recall_latency.py:22-25）：ordinary p95 ≤ 3000ms、assisted max ≤ 10000ms，通过 caller_assistance.calls==1 区分。gate 结果被 governance 的 release_lineage:1124-1155 和 l5_readiness:658-677 直接消费，构成 release 发布门限。

5.3 标签权威链与 reward 引擎

  

    

三层标签权威设计清晰
：label_authority（单一标签验证入口，区分 operator/delegated_ai）→ dataset_authority（dataset 级别完整权威链：collector→label→pending→candidate）→ delegated_label_authority（AI 委托标签 HMAC 签名/验证/实时性检查）。delegated 路径需要 HMAC 签名 + delegation packet 验证 + 实时 digest 匹配三重校验。与 capability_catalog 是独立的权威链（catalog 管 executor/case 注册，label_authority 管生产标签）。

    

RewardEngine
（reward.py，59 行）：极简确定性 reward = recall_quality + 2*success + eval_bonus - cost + failure_penalty。问题：
recall_quality 直接从 eval_result.get("recall_quality") 读取
，但 production_recall 报告产出的是 hit_at_1/hit_at_5/mrr 而非 recall_quality——传入 production_recall 报告时 recall_quality 恒为 0.0（中危）。_success_value 文本匹配集 {"success","good","passed","pass","ok"} 未包含 "completed"/"succeeded"（task_replay 认可的 status），若 outcome 使用这些词将错误判定为失败（中危）。

seal() 与 _require_mutable() 无锁保护，check-then-act 非原子。多线程并发 bootstrap + seal 时一个线程可能在 _require_mutable 通过后被另一线程的 seal() 插入。正常部署单线程顺序执行（_APPLICATION_CATALOG_LOCK 内先验证再 seal），实际无利用路径。

    
capability_catalog.py:420-434

    

修复建议：
给 CapabilityEvaluationCatalog 增加 RLock，在 seal() 与 _require_mutable() 中持锁。

evaluation 模块审计结论

    
evaluation 是全项目
安全设计最严密的模块
：capability_catalog seal/fail-closed/证据链验证、real_query_gate 多层摘要防篡改 + 重算校验、标签权威三重校验、delegated_review 事务内 TOCTOU 缓解——这些设计在同类本地工具中显著高于平均水平。

    
三类技术债：
契约层完全缺失
（0 Protocol / 17 处裸访问 store 私有成员 / 10 处私有跨包导入）；
上帝文件 hub
（real_query_gate 3152 行 / 5 条循环依赖 / 3 处静默吞没）；
错误处理双标
（catalog 链路 fail-closed 严密 vs benchmark 适配器 7 处 pass/return []）。另需注意 tracemalloc 外部 tracer 导致 gate 永远 blocking 的阻断性 bug。

    
P0 三项（tracemalloc 修复、store 公共只读接口、外部数据集校验）落地后，release 阻断解除、并发隐患消除、生产污染面封堵。P1 完成后模块内循环依赖归零、benchmark 错误可观测、reward 信号正确。
