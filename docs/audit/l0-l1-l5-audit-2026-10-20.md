# L0/L1 召回算法与 L5 业务闭环审计

日期：2026-10-20（Asia/Shanghai）。

## 结论与基线

本轮以 `darrowz/eimemory` 的 `master` 提交 `c883a9352853f42bc693a0c2148418a0f4657a2a` 为唯一补丁基线，项目版本为 `1.14.156`。此前版本的审计报告仅作为问题线索；本轮缺陷均重新对照当前源码和离线复现验证。

补丁覆盖 L0 原始证据排序、L0/L1 召回融合和页面去重、L1 提取及事务恢复、L5 验收与回放证据绑定，共 25 个文件：12 个生产代码文件、12 个测试文件与本报告。审计范围以这些调用链为边界。

**代码与离线行为可以验证；当前生产环境的 L5 完成状态尚无本轮证据。** GitHub 源码、单元测试、服务健康、operational probe 或通道 `platform_accepted` 均不能替代真实业务的终态回执。本轮没有连接生产数据库、调用真实 LLM、发送业务消息或执行生产部署。

召回策略身份升级为 `governed-recall.v4`；RRF 数学公式仍为 `governed-rrf.v1`。策略身份摘要随之改变，旧策略的验收身份不能直接证明新算法已经验收。

## 一、核对的实际调用链

### L0 与 L1

`sync_turn / l1_worker` 捕获 L0 后进入持久队列；`extract_l1_from_l0_record` 精确读取实际来源，再经 `extract_l1_atoms`、`adjudicate_l1_atoms`、`persist_l1_atoms` 写入 L1。`RuntimeStore.append_and_supersede` 在同一存储事务中提交新事实、旧事实的 superseded 状态、关系和导出 outbox。L0 提取完成标记由随后独立事务写入，最后队列 ACK。

这里有两个独立的事务边界：child 已提交不代表 L0 完成标记已成功；队列 handler 返回也不代表 ACK 已记录。修复及回归以实际持久化结果为准。

常规召回经 `MemoryAPI.recall` → `GovernedRecallEngine` → 候选来源与精确权威回读 → RRF 融合 → 同页代表选择 → 相关性准入 → 最终权威核验。L0 的 raw-hybrid 证据另经 `raw.retrieval`，与结构化 L1 保持各自的准入路径。

### L5

发布身份与正式 pending → capability replay/bootstrap → live acceptance operational probes → 外部通道回执 → rehearsal/readiness → v3 控制面评估 → v4/v5 产品完成判定。

其中真实任务回放及产品终态凭据具有独立的来源、执行批次和发布谱系约束。bootstrap 失败会阻止后续阶段；不能把后续 `live=0` 单独解释为 live 实现失效，也不能将已接受的请求解释为业务消费完成。

## 二、L0 与召回算法修复

| 编号 | 根因 | 补丁行为 | 主要验证 |
| --- | --- | --- | --- |
| R01 | `raw._terms` 把整句中文或中英相邻文本作为一个词，短中文名称与 `L1` 等标识符缺少词法交集 | 中文使用连续双字片段，非中文词保留原有标识符边界；无需新增分词依赖 | 中文短名、中文词、中英混合标识符补充检索 |
| R02 | 补充扫描保留相关性为零的记录，随后更正/时间加分使无关记录看似有效 | 先要求查询相关性为正，再参与排序；未知问题不会靠无关更正填满返回槽位 | 未知查询应返回空；保留损坏/不完整集合的 unavailable 区分 |
| R03 | 索引与补充候选分别重排，最后固定主列表优先；还各自获得不同的“最新”时间奖励 | 联合候选统一排序，使用同一时间参照；新纠错可与已索引旧事实竞争 | 新更正先于旧断言，分数和顺序一致 |
| R04 | 相同精确引用重复出现可占用多个交付名额；非有限分数可霸占排序或抛出溢出异常 | 按完整记录身份、作用域和 source 去重，保留最强一次基础分；拒绝非有限或溢出分数 | 重复候选不挤掉第二条证据；Infinity/溢出输入保持有限输出 |
| R05 | usage 有反馈即入 RRF，living 非零即入 RRF，导致负值/净零信号变成正排名票 | 仅净正 usage、正质量或正 living 信号产生对应分量的正票 | 负反馈与净零反馈不反向提升；真正正反馈仍有效 |
| R06 | 同页先保留高分无关片段，后续准入将整页丢弃，页内有依据的片段已被遮蔽 | 默认本地准入使用既有规则选择自身有证据的同页代表；替换代表按自身融合位置参与页面间排序 | 中英文同页遮蔽、所有片段无关、代表自身分数与页面诊断总分隔离 |

R03 经独立复核保留了原 locomo turn 上下文的触发顺序：先尝试邻接扩展，只有数量仍不足才调用补充扫描；需要扫描时再对原候选和扫描结果统一重排、按需扩展。对应的回退回归已纳入测试。

R06 沿用 `authority_gate` 的精确权威规则。真正 selector 接收的 `pool_members` 被规范为代表自身，不能借用兄弟片段的身份、相关性或分数。原页面成员和 `aggregate_score` 仅用于解释诊断。该修复针对默认本地准入，外部 reranker/LightweightAdmission 保持各自的独立策略。

这些改动没有引入未经校准的负 RRF 权重，也没有将一条拒绝反馈当作永久禁止召回。原有召回门槛保留；改动修正的是候选资格、证据归属和处理顺序。

源码：[raw/retrieval.py](../../eimemory/raw/retrieval.py)、[retrieval/engine.py](../../eimemory/retrieval/engine.py)。

## 三、L1 提取、纠错与恢复修复

| 编号 | 根因 | 补丁行为 |
| --- | --- | --- |
| W01 | 冲突候选检索忽略 degraded 标志，超时空结果会成为“无旧事实”，部分结果也会进入裁决 | 空或部分的不完整搜索均产生 `l1_conflict_candidates_incomplete`，在写入 child 和 L0 完成标记之前停止，并记录明确诊断 |
| W02 | `target_ids` 接受字符串，随后却按字符迭代 | 单字符串表示一个完整 ID；数组及候选池目标授权检查继续生效 |
| W03 | 非空 `episode_id` 不存在时降为无绑定写入，产生悬空来源链接 | 必须找到精确父 L0，否则 `l1_source_parent_unavailable`；分区不匹配保持独立错误 |
| W04 | 失败作业立即回到队首，同一 drain 可一次耗尽五次尝试 | 单次 drain 内每个 job 至多尝试一次，继续处理其他作业；失败留待之后 drain，五次总上限及进程锁保留 |
| W05 | 合并 child 已提交、前驱已关闭，但 L0 完成事务失败；重试默认 store 与已提交合并文本冲突 | 通过随 child 同事务保存的写入凭据恢复已经提交的裁决；来源、原 atom、最终内容及完整裁决受一致性约束 |
| W06 | 恢复时只检查部分 inactive 枚举，archived/draft child 可被报告为 written 并把 L0 置为 stored | 被计入 written 的 child 必须为 active；非 active 记录保持原状态且不计写入，本轮无其他 child 写入时 L0 记为 no_change |

W05 的恢复只允许明确的 `no_candidates + store` 默认路径。`ConflictDecision.origin` 区分实际 Judge、默认无候选与宽松回退。精确 child、L1 提取身份、父来源摘要与观察时间、最终内容及写入凭据在 SQLite 写入事务中再次核对。恢复不会重新 ingest，也不会发起新的 supersession。对于已有完整写入凭据的 child，真实 Judge 的决策漂移必须拒绝，即使最终文本相同但目标或动作变化也不例外。

凭据的 `decision_digest` 绑定 action 与去重排序后的目标集合。完全相同的 Judge 裁决可幂等复用；相对于已提交裁决发生的动作或目标变化不能绕过比对。有凭据的 child 不进入旧版 reconcile 路径；旧版 repair 的第二个事务也再次检查凭据，防止两次事务之间状态变化带来新的纠错目标。

新元数据通过现有记录写入，不需要数据库 schema migration。无凭据的旧 child 保留原有内容一致时的幂等复用，以及受实际来源和时间约束的 pre-v2 reconcile；对于缺失原始合并裁决的记录，不凭空恢复其最终内容或目标集合。旧数据的失败状态仍需针对实际来源和已提交关系另行核实。队列修复保证单次 drain 的公平性，没有额外引入持久化指数退避；跨 drain 的频率仍由原调度决定。

源码：[l1_conflict.py](../../eimemory/knowledge/l1_conflict.py)、[l1_pipeline.py](../../eimemory/knowledge/l1_pipeline.py)、[l1_queue.py](../../eimemory/knowledge/l1_queue.py)、[l1_diagnostics.py](../../eimemory/knowledge/l1_diagnostics.py)。

## 四、L5 业务闭环核查与修复

| 编号 | 根因 | 补丁行为 |
| --- | --- | --- |
| G01 | 同一 case、receipt、session 的新失败被跳过；秒级时间与随机 ID 排序不能证明观察先后；内容幂等还可能把恢复成功折叠为旧成功 | 按原生存储插入顺序取得最新匹配观察，包含失效状态；真实执行产生独立观察身份，缓存命中保留幂等 |
| G02 | 只校验回放报告顶层代码摘要，样本可来自旧代码或其他执行；损坏样本可被剔除后用剩余成功样本稀释 | 校验报告身份、scope、执行 ID、样本类型，并逐样本绑定当前代码摘要和本次执行；来源/终态证据损坏产生显式真实性失败 |
| G03 | 外部回执的幂等键缺少发布 receipt/session，写入结果未精确回读，时间戳可被隐式强制转换 | 幂等键绑定 receipt/session；返回成功前以 exact ref 和 source 回读 active 完整证据；时间戳必须为正 JSON 整数 |

真实性失败原因由 real replay gate 统一定义，closure rehearsal 使用同一集合，避免同一损坏在两个门禁中得到相反含义。回放报告不存在与已存在但身份损坏分别报告；后者保留记录 ID，便于定位。原本非业务/演练样本维持正常排除语义；曾经已验证的来源发生变化则不能悄悄删除后继续通过。

G01 使用已有的 `latest_record_by_meta_value_exact_scope` 插入高水位合同（SQLite `rowid DESC`），限定 scope、producer source、kind 和 commit/receipt/session/case 身份键。helper 默认仍筛选 active；live 缓存显式使用 `status=None`，使最新 quarantined 记录也能阻止旧成功复用。旧成功经过 rewrite 不改变原生插入顺序；没有新观察键的历史记录重新执行探针，不回退到时间排序列表。实际探针使用独立 `observation_execution_id`，绑定 observation digest 和 `live_task_acceptance.v3` 幂等键；相同内容的恢复成功得到新的 record/trace，随后缓存可复用这次新成功。该调整使用既有表和查询机制，不新增 schema migration。

### 证据判定矩阵

| 环节 | 当前代码需要的证据 | 本轮结论 |
| --- | --- | --- |
| L0 → L1 → 常规召回 | 来源绑定、active fact、旧事实 superseded、最终授权召回 | 已用真实本地 SQLite 和固定模型边界贯通；包含中文纠错与跨用户隔离 |
| 发布身份 | 实际 release receipt、commit、session、作用域与当前谱系 | 已核对代码并用本机临时 HTTP fixture 验证；未取得生产当前回执 |
| replay/bootstrap | 同发布身份的实际执行及完整结果，失败不能放行后续阶段 | 相关离线合同验证；不作为生产执行回执 |
| live acceptance | 最新 case 观察、trace 和精确发布/session 绑定 | 已修复旧成功掩盖新失败；仍属于 operational probe |
| 外部渠道 | 可信 transport 的平台接收回执及当前/合法继承通道绑定 | 已加固持久化和身份；`accepted`、字符串 `200` 不合格，`platform_accepted` 仅证明通道可用性 |
| 真实任务回放 | 当前代码、同执行批次、真实终态链、至少 10 个有效样本、通过率至少 0.8 | 保留原数量和通过率门槛，增加真实性约束；没有本轮生产样本 |
| 产品 L5 | 控制面、provider/catalog、系统自主来源、合格终态、观察窗口和兼容谱系 | 缺少当前生产完整凭据，不能认定 `product_l5_complete=true` |

产品层合格终态仍为 `succeeded_sedimented`、`rolled_back_healthy` 或 `quality_repaired`，且须符合实际观察、来源与发布证据。人工 bootstrap、预先已知或用户先报告的事件不能凭本次审计变成自主发现证据。一次修复提交、一次测试成功或一次通道回执都不能替代这些条件。

## 六、应用与现场验收

在包含基线提交的干净工作树中：

```bash
git switch -c honda/l0-l1-l5-audit-20261020 c883a9352853f42bc693a0c2148418a0f4657a2a
git apply --check /absolute/path/eimemory-l0-l1-l5-20261020.patch
git apply /absolute/path/eimemory-l0-l1-l5-20261020.patch
python -m compileall -q eimemory
git diff --check
```

交付包的验证清单列出完整受影响测试命令。若目标主线已前进，应先在独立分支检查并合并新改动，再重新执行受影响验证。该补丁没有自动部署步骤。

现场验收应保存实际运行代码摘要和 `governed-recall.v4` 身份，重新核对已知团队分工、纠错优先级、不存在内容、作用域隔离及错误恢复，再对同一 release/session 取得 replay、live、外部通道与真实业务终态证据。对于历史 L1 中缺少凭据或来源时间不明的记录，应保留明确失败原因，不伪造时间或裁决来批量置绿。

代码回退可先用 `git apply --reverse --check` 检查反向补丁；已经写入的数据和真实业务结果具有自己的审计历史，源码回退不代表数据历史回退。

## 七、当前证据边界

本轮证明指定代码路径中的确定性缺陷已修复，并验证相关行为和权威边界。没有测量生产真实查询集的 recall@k、MRR 或 p95 延迟；不报告未经测量的提升百分比。远端向量服务、实际 LLM 抽取质量、生产队列历史和当前 L5 产品完成状态仍需各自的运行证据。

完整补丁以本报告所列基线及交付清单为准；最终文件散列可用于识别补丁、测试日志与应用结果，避免混用旧版本审计材料。
