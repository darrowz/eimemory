## 修复

- L1：安装已有 worker service/timer，首次部署也生成 immutable runtime 身份，复制失败即停止，正常路径只启动一次 timer。注册 manager 仍由原 controller 发布/恢复；fused closure 只暂停、评估与恢复既有 L1 owner，不增加消费者。
- Capture：新增 `deploy/repair_capture_scope_dropin.py`。正式 immutable installer 的预检与元数据安装/回滚路径会验证并重写既有 `eimemory-rpc.service.d/95-release-scope-binding.conf` 的 capture JSON 转义。整个赋值被引用，内层 JSON 的引号、反斜杠及 systemd `%` 得到保留；不开启开关，不增加 scope，不读取生产对话。
- Cron/operator：provider 保存服务端 `acceptance_generated`，observer 不再发送被自然证据边界必然拒绝的信号。旧重试项只在服务端明确返回 `effect_signal_acceptance_decision_rejected` 后移除；认证、scope/source 和其他失败继续 fail-closed。
- RPC：500 在 journal 与最多 64 KiB 的 `logs/rpc-errors.jsonl` 记录日期、有限方法名、固定错误码、白名单异常类别。没有请求参数、凭据、原始文本、异常消息或 traceback；诊断失败不改变 HTTP 500。
- 发布 gate：将既有 `deploy/reconcile_managed_authority_to_current.py` 及新 capture helper 登记为 `deployment.runtime` 的具体路径，保留未知路径拒绝。

## 父级部署与观察边界

1. 审核本补丁并沿原正式发布流程部署；普通 user-manager 路径会自动再生成上述既有 drop-in。注册 system/user controller 路径仍须经过既有审核的 controller/template 流程，不允许候选代码新增服务归属。不要手改 immutable release、直接清空 queue 或开第二个 worker。
2. 切换后只输出 capture JSON 可解析性、scope 数量和 canonical digest；应与部署前磁盘有效 JSON 的 3 个既有精确 scope 一致，capture 开关不变。有效 process 环境需重新加载后核验；单纯修好磁盘文件不是完成验收。
3. 确认 L1 owner 的 manager、unit identity、timer 状态和日志日期/计数；队列应有界下降，dead/失败不得被隐藏。旧 queue 依赖既有 consumer lock、精确 source/scope、去重及 source ordering。
4. 独立重跑 loopback HTTP 合同；观察下一次真实 cron 的信号失败计数与固定错误码。历史失败 ledger 不重置。
5. `adapter.attest_tool_result` 的历史单次 500 仍缺异常证据；如复发，按日期/方法/异常类别检索新有界日志。`hermes_explicit_host_session_mismatch` 没有新的现行复现，保留独立绑定检查。
6. 自然质量门禁、L5 与当前发布 48 小时闭环仍需真实新证据。capture 可用、pending 下降、基础运行正常都不能代替这些结论，11 月 6 日旧 L5 报告不可用于本版本关闭。

回滚继续使用原 immutable installer 的恢复边界。scope helper 只改变表示，不撤销/增加 opt-in；queue、原锁与历史错误保留。技术提交后的后台恢复失败必须继续报告并由原 owner 重试，不以旧快照覆盖后续写入。
