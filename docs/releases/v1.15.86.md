# 1.15.86 — bounded recovery from concurrent projection commits

The deployed 1.15.85 release passed its qualified operational known-item cohort
at **15/15** and authenticated RPC checks at **3/3**. Replay, live acceptance,
channel provenance and release lineage also passed. The formal attempt still
ended degraded: its final projection maintenance returned a generic runtime
error before the final read-only readiness barrier was entered.

Read-only journal evidence shows that the background vector worker committed
30 records and advanced the index while the formal maintenance was still
running. Subsequent native observations found SQLite, PostgreSQL and the serving
endpoint on the same revision and watermark, with zero lag. The saved failed
receipt retains its original outcome. The concurrent timing matches a
reproduced protocol defect. The erased original exception code leaves the
precise historical cause unverified.

## Change

An incremental projection commit compares its expected generation, revision and
fingerprints with the locked PostgreSQL state. A competing writer can advance
that state while the first writer is computing embeddings. The first writer
must preserve the newer projection. Previously the repository erased the
specific conflict code, and the public maintenance layer reduced the remaining
error to `RuntimeError`.

This release preserves a safe conflict outcome and permits a bounded re-read
only for that conflict. Recovery requires demonstrable forward progress within
the same compatible committed generation. Unknown failures, incompatible
fingerprints, generation changes, rewinds and unchanged conflicts remain
failures. A successful maintenance result still requires current authority;
formal acceptance still checks the native read-only barrier and the serving
endpoint's matching revision and watermark.

## Validation status

Both required CI workflows include conflict recovery and independent failure
cases. Candidate measurements and CI results must identify the exact source
commit. Formal business closure requires a fresh persisted native receipt.

The focused projection regression passes **362 cases**. Fourteen independent
cases use the real SQLite journal and repository transaction code with a
synthetic PostgreSQL connection. The same frozen cases improve from **11/14 to
14/14**, including bounded concurrent recovery and rejection of incompatible
state. Their input and expected-result file remains unchanged.

The preserved original fifteen-case recall cohort returns **10/15** before and
after 1.15.85. The prior qualified operational cohort returns **15/15**. The
1.15.86 synthetic 200-question RAW replay retains Top-1 **109/120** and Top-5
**119/120**, with zero hit-order changes. These measure document ranking.

## Remaining performance limit

The previous formal attempt also exposed a separate budget gap: a restore
declaring a 120-second budget completed after about 160 seconds. Its loop checks
leave internal embedding and PostgreSQL operations without an end-to-end
deadline. Strict deadline propagation remains unfinished.
