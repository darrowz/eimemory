# eiMemory 1.15.26

This release consolidates the source changes since the previous GitHub release,
**1.14.101**, including the 1.14.102–1.14.156 and 1.15.0–1.15.26 changes and the
October 23–24 follow-up repairs. Python **3.11 or newer** is required.

## Recall and durable memory

- Keep lexical FTS candidates alongside hybrid and PostgreSQL recall with a
  bounded lexical reserve. Split mixed CJK/ASCII query terms and retain exact
  scope isolation, grounding checks and deadlines.
- Use the actual host request for answer admission when contextual expansion is
  used for retrieval. Retry the literal request after an empty expanded recall,
  exclude the just-captured current request from delivered evidence, and skip
  automatic recall for host gateway/background notifications.
- Prefer durable delivery preferences for procedure, deployment and acceptance
  queries. Preserve complete bounded conversation spans and original-source
  bindings in compact recall.
- Repair L0/L1 recall ranking, governed page selection, durable conflict recovery
  and fair queue draining. Refresh reviewed knowledge when its support changes,
  with exact authority and original-source checks.
- Add governed identity views and individually authorized legacy Hermes subject
  projections. Original records and signatures remain available; current
  retrieval rechecks source versions and authority.

## Recall policy changes to review before upgrading

The active policy is **`production_recall_gate_policy.v6`**. Its temporary
absolute ranking floors are **MRR ≥ 0.50** and **nDCG@5 ≥ 0.55**. Historical
policy v5 payloads retain **0.80 / 0.80**, and trusted historical baselines are
validated against their recorded supported policy. The temporary floors are
not evidence that ranking quality has recovered.

Pollution and leakage constraints, the other metric limits, scope checks and
baseline non-inferiority checks remain in force. Missing or inconsistent
required evidence still blocks acceptance.

**G2c** forces separate recall evaluation for authorized agents or topology-bound
profiles that have natural traffic. Declared profiles without such traffic
remain visible in inventory and sampling diagnostics, but do not independently
block the combined result. Results are not pooled across agents; each forced
scope must pass. This verdict covers the evaluated traffic scopes and does not
establish quality for every installed profile. The **G3 semantic judge** retains its
`max_new=8` limit.

See [evaluation policy](https://github.com/darrowz/eimemory/blob/v1.15.26/docs/evaluation.md)
and [agent discovery](https://github.com/darrowz/eimemory/blob/v1.15.26/docs/deployment/agent-discovery.md)
for the detailed contracts.

## Hermes, deployment and recovery

- Follow one native Hermes gateway with multiple logical profiles throughout
  request identity, sampling, acceptance and recovery. Keep gateway execution
  under native host configuration and store memory handoff state privately.
- Capture real explicit recall calls with their host invocation and original
  source identity. Nightly independently reviews signed results; natural query
  quality and answer contribution retain their own evidence requirements.
- Use ordinary user service management for ordinary deployment. Add reviewed
  controller upgrades, user recovery and native process observations with
  authenticated owner, invocation, PID and cgroup boundaries.
- Restore core serving before business acceptance, then restore captured
  background services, timers and paths. Preserve original recovery captures,
  failed native outcomes and exact final readback through interrupted attempts.
- Recover incomplete controller publication from verified original inputs and
  permit reviewed abandonment of specified failed deployment states without
  rewriting their failed evidence.

## Readiness, storage and operational evidence

- Observe current PostgreSQL readiness with a bounded read-only vector query and
  consistent authority snapshots. Distinguish index lag from authority changes
  during the probe, and retain prior business-query diagnostics independently.
- Catch up the vector projection after storage transaction guards clear before
  starting readiness acceptance and stability observation. Settling respects
  the configured maximum index lag; failed restoration remains a failure.
- Add operator-authorized controlled acceptance of existing memories with exact
  source/version grants, native provenance and current-release receipts. Keep
  historical business qualification, natural traffic and generic diagnostic
  checks explicit in the reports.
- Bind release lineage, replay, channel, live-task and stability evidence to the
  actual release and owner. Report intentional controlled-path recall/L5 skips
  with explicit reason codes.
- Persist native L5 assessments and exact-source incident evidence. Retain
  immutable owner history and bounded signed archives during managed recovery.
- Bound backup export memory through a lean reader and disk index, preserve
  complete verification, and support configured backup/release retention.

## Downloads and installation

The [GitHub release](https://github.com/darrowz/eimemory/releases/tag/v1.15.26)
provides:

- `eimemory-1.15.26-py3-none-any.whl` — installable Python package.
- `eimemory-1.15.26.tar.gz` — Python source distribution.
- `SHA256SUMS` — checksums for the uploaded distribution files.
- GitHub's tagged source archives — the full source, integrations and deployment
  tooling at the release tag.

Download the distribution files and `SHA256SUMS` into the same directory, then
verify them before installation:

```bash
sha256sum --check SHA256SUMS
python -m pip install --upgrade ./eimemory-1.15.26-py3-none-any.whl
```

The core package has no mandatory third-party runtime dependencies. Install the
extras needed by your integration; for example:

```bash
python -m pip install --upgrade './eimemory-1.15.26-py3-none-any.whl[pdf,postgres,hermes]'
```

For a source installation that also includes integration and deployment files:

```bash
git clone --branch v1.15.26 --depth 1 https://github.com/darrowz/eimemory.git
cd eimemory
python -m pip install '.[pdf,postgres,hermes]'
```

For an existing managed deployment, use its reviewed deployment and recovery
procedure with the tagged source, preserve a verified backup and collect fresh
acceptance evidence for the resulting release. Replacing a Python package alone
does not perform controller migration or establish deployment success. See the
[deployment guide](https://github.com/darrowz/eimemory/blob/v1.15.26/docs/deployment.md)
and [deployment documentation](https://github.com/darrowz/eimemory/tree/v1.15.26/docs/deployment).

## Validation scope and complete history

Vector projection restoration is now registered in the recall, governance,
storage-integrity and deployment-runtime release domains, fixing the missing
production-file classification that blocked both CI suites. Publication requires
Project validation and Linux deployment contracts to pass on the exact same
source commit, plus package version/contracts checks, distribution builds and
an installed-wheel smoke check.

This is a source and package release. GitHub CI and packaging verification do
not establish current production deployment, natural recall quality or L5
completion. Dated production receipts retain their original version, source,
scope and outcome; a new deployment needs its own evidence.

The package, runtime version, Codex plugin and managed Hermes plugin manifests
use **1.15.26**. The private OpenClaw bridge keeps its separate package version.
