# eimemory 1.15.69

## Summary

Native policy prior-retirement no longer deadlocks when release-closure capture still says `failure_detected` for a *different* incident that CE selection already ops-dropped (projection lag / oneshot quiet). Hermes `native_policy_owner` can retire an unrelated unconsumed prior instead of staying blocked on `prior_policy_currentness_unverified`.

## Why

Tips 1.15.65/1.15.67 correctly stop auto-routing sticky ops-timing closure incidents once live readiness is restored. Capture markers can remain `failure_detected` for that dropped incident. The prior-retirement fence then treated "sticky failure for some other incident not in `current`" as unverified currentness, freezing any unconsumed Hermes prior (e.g. older tip's `release.closure_*` policy) and failing nightly `code_evolution` even when Admission gates were green.

## Change

- `code_automation_policy_owner._verify_prior_unconsumed_retired`: for `release.closure_*`, only the prior policy's own `capture_id` / `incident_record_id` block retirement (remove the unrelated sticky-disposition clause).
- Test: `test_sticky_unrelated_ops_dropped_failure_does_not_block_prior_retirement`.

## Ops

Deploy tip; refresh code-implementation advertisement; re-prove CE with registered Hermes owner idle or able to issue. No schema/migrate. ChatPaper stays disabled. Admission re-enable is independent once CE is green.
