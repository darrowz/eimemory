# 1.15.87 — bounded maintenance and observable host lifecycles

Projection restoration previously checked its budget around calls that could
overrun it. One isolated native-path measurement declared 120 ms, took 330 ms,
and accepted all eight records after the budget. The same measurement now
returns incomplete in 87 ms after safely committing two records. Late pure
work leaves that count unchanged; a subsequent invocation completes all eight.
This is a controlled local experiment, not a production throughput benchmark.

## Maintenance behavior

One monotonic deadline covers the worker, SQLite lock/read scopes, pure
embedding and connection work, and dedicated PostgreSQL maintenance
connections. Pure work that outlives its caller retains a globally bounded
slot until it exits. PostgreSQL writes remain on the caller thread; every
statement receives the remaining budget. A Linux socket watchdog interrupts
blocked reads on that connection alone. An acknowledgement lost after COMMIT
is explicitly unknown. It cannot certify success or a definite rollback.

Small checkpoints permit safe resumption within the existing 300-second outer
release budget. Each maintenance slice retains its 120-second cap. A final
read-only barrier and a matching serving-listener revision and watermark are
still required. Real errors stop recovery immediately.

The focused projection regression passes 275 cases on both Linux and Windows.
In an isolated loopback protocol experiment with psycopg 3.3.9 and an 80 ms
budget, a blocked read returns in 81 ms without COMMIT; a missing COMMIT
acknowledgement returns in 97 ms with an unknown outcome. No production
database is used. Windows native socket hard deadlines are explicitly
unsupported. Calls without a deadline retain their existing behavior. These
budgets do not promise forced termination of arbitrary Python callbacks or
kernel filesystem operations.

## Host observations

Initialization, ownership conflict, rotation, closure and actual recall
results emit fixed-schema digest metadata. A conflict identifies attempted
and retained namespaces separately. Initialization alone does not prove
recall availability. Existing cross-owner protections remain enforced.

Optional `EIMEMORY_CAPTURE_ANSWER_OBSERVATIONS=1` uses the existing exact
query-capture scope policy. It binds the complete callback body to the
original pre-call query, current provider owner and an explicitly observed
post-call host turn. Missing, inferred, conflicting or oversized inputs emit
no complete-answer observation. It stores no answer body and does not add
new effect-signal ledger phases. The feature is disabled by default.

Sixteen answer-observation cases and thirteen session-observation cases pass.
Two independent overlap/query-consistency probes initially failed and pass
after the callback binding was tightened. These counts measure observational
contracts, not final-answer accuracy. The Windows receipt fixture normalizes
its synthetic release paths without relaxing production identity checks.

## Acceptance boundaries

The original synthetic RAW 200-question replay retains Top-1 109/120 and
Top-5 119/120 with zero hit-order changes. A new release still needs required
CI and its own persisted native closure receipt. Prior operational cohorts,
synthetic rankings, callback labels and healthy services cannot certify
natural answer correctness or L5 task success.

The original ten initialization alerts lack individual session evidence.
New observations cannot reconstruct them. Missing historical control-plane
keys and custody materials cannot be regenerated as historical evidence.
Fresh current-state enrollment and independent natural-answer review remain
separate work; this release does not claim their completion.
