# eimemory 1.15.78 — opt-in structured temporal facts

## Included scope

This release adds `MemoryAPI.apply_temporal_facts` and `MemoryAPI.recall_temporal_facts` at a trusted Python boundary. It reuses canonical RuntimeStore/SQLite records, evidence links, atomic transactions and `living_memory_v1` metadata. No new database, graph framework, runtime dependency or production-data migration is introduced.

The API requires explicit caller-bound `TemporalFactAccess` and `enable_temporal_facts=True`; the default remains disabled. No RPC tool, automatic L1 extraction, normal chat behavior or production flag is enabled by this source release. The rejected experimental RAW-ranking patch is excluded; its benchmark gains are not claims for this release.

## Contracts

- Exact namespace, string entity ID, attribute, applicability, source authority and access partition define the fact family. Leading-zero IDs remain distinct. Single and multi-valued facts are distinguished; overlapping independent claims are not resolved by arrival order.
- Explicit valid intervals use `[valid_from, valid_until)`. Unknown bounds are distinct from unbounded ones; ingestion time is not fabricated into a business effective date. Future changes do not invalidate earlier facts immediately.
- Claims, transitions, interval-local corrections and retractions append immutable revisions with original evidence and server-recorded time/order. Retraction does not silently revive a predecessor. Unsupported `known_at` replay explicitly fails closed.
- Complete family reads use one consistent snapshot. Missing/unsafe original evidence and over-budget families do not produce a partial winner. CAS, idempotency, targets and scope/source checks remain transactional.
- Generic rewrite/replay paths protect persisted revisions before deletion/mutation, even when incoming metadata is stripped. Source bindings must be canonical. Evidence-admission callbacks receive isolated snapshots; mutation is rejected and cannot substitute another proof.
- Legacy readers exclude inactive revision evidence from ordinary current recall. Generic legacy writes, source-order policy and datetime behavior are not reinterpreted.

## Isolated acceptance

The reviewed eight-file implementation passed a contained parent batch of **330 main tests and 60 subtests**, without failures or skips. These include temporal functionality, independently reproduced security-boundary cases, legacy L1 source order, runtime RPC, storage transactions/concurrency, retrieval, living metadata and RAW regression contracts. The first producer was interrupted with exit137; its exit is not counted as success. Parent execution and subsequent repair acceptance are separate evidence.

A parent-authored semantic oracle, withheld from implementers, covers nine synthetic scenarios and **17 query points**. All17 match the expected values/conflict behavior; all17 results are identical after closing and reopening their real temporary stores. Scenarios cover future boundaries, historical queries, limited retroactive correction, late disjoint facts, exact IDs, distinct attributes, conflict, multivalue and no resurrection after retraction. An empty API `absent` result is treated as no current fact, not as a resolved positive assertion.

These are structured API/store correctness checks, not natural-language extraction accuracy, ordinary-chat improvement, complete dual-time history, production SLOs, L5 or 48-hour observation. Final package metadata checks and immutable deployment verification are separate gates; a source version or successful test does not imply deployment.

## Rollout and rollback boundary

Keep the new entry point disabled by default. Enabling a future adapter requires separate authenticated identity/evidence binding and natural-language acceptance. No legacy evidence is rewritten or deleted. Existing inactive/hidden semantics prevent revisions leaking into old-reader current recall; preserve appended evidence on rollback rather than resetting production data.
